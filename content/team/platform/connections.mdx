# Connections Architecture

## The connection model

Synap separates account management from Pod data access. This keeps a self-hosted Pod useful without Synap Cloud and lets a Pod owner trust a different account service later.

| Connection | Authority | Credential / proof | Purpose |
|---|---|---|---|
| App ↔ account service | Account service | Account-service session | Sign-in, recovery, invitations, billing, and Pod discovery ledger |
| App ↔ Data Pod | Data Pod | Pod-local Kratos session or API key | Data, workspaces, projects, membership, and all user actions |
| App ↔ Data Pod (federated entry) | Data Pod | Short-lived issuer assertion, exchanged directly | Create a Pod session for an already-linked local user |
| Data Pod ↔ Intelligence Hub | Data Pod / Hub Protocol | Hub Protocol API key | AI reads and writes through governed Pod APIs |
| Optional Pod agent ↔ operations service | Pod owner | Separate signed command protocol | Explicitly enabled lifecycle operations only |

The Control Plane is one possible account service and operations service. It is not part of a Data Pod's user, membership, or session schema.

## Account service and Pod access

An account service owns its users and a ledger of their known Pods. That ledger answers _which Pods should we offer this person?_ It does not decide whether a person can access a workspace or project inside a Pod.

```text
account session -> account-service ledger -> short-lived user-exchange assertion
browser -> selected Pod /api/federation/exchange -> Pod-local session
```

The browser sends the assertion directly to the Pod. The Pod verifies an owner-approved issuer, its exact audience, expiry, purpose, and one-time identifier. It resolves a generic `(issuer, opaque subject)` identity link, checks its own membership, and mints the session. No raw Pod token travels to the account service.

### Pod selection and reload

Clients restore account and Pod sessions independently:

1. Restore the account session.
2. Read the account service's Pod relationship ledger.
3. Directly connect if there is one eligible Pod; otherwise show a picker.
4. If the user has no relationship, offer to add an existing Pod URL or follow the product's provisioning path.
5. Preserve the account session if a selected Pod is offline, lacks a workspace, or rejects access. Offer another Pod or direct Pod login instead of forcing account sign-in again.

## Adding a Pod to an account

An account service must prove that the person already has direct local access before adding a Pod relationship:

```text
account service creates identity-link intent
browser receives identity-link assertion
browser (direct Pod session) -> /api/federation/identity-links
Pod returns opaque receipt
account service consumes receipt server-to-server
account service records Pod-authoritative access in its ledger
```

The direct Pod session never crosses to the account service. A relationship may be Pod-wide, workspace-scoped, or project-scoped, according to the access the Pod reports.

## Invitations and grants

An account service may deliver and track invitations. When the recipient has an account, it sends an `access-grant` assertion directly to the Pod's `/api/federation/access-grants` route. The assertion identifies one exact local workspace or project. The Pod verifies the issuer's `membership:grant` capability and applies its own membership rules.

Direct invitations made inside a Pod remain fully supported and do not require account-service connectivity.

## Direct Pod access

The direct Pod login, recovery, and local invitation flows are first-class. They are not error fallbacks for Control Plane access; they are the sovereign path for self-hosted Pods and for account-service outages.

Apps can use Pod API keys for machine access where appropriate. AI and agent services use Hub Protocol for data access so `checkPermissionOrPropose()` remains the governance gateway.

## Intelligence Hub connection

The Intelligence Hub does not receive an end-user federation assertion. It authenticates to the Pod with a Hub Protocol API key and calls `/api/hub/*`. The Pod triggers agent runs through the Hub's service API. These are service-to-service credentials, separate from user login and trusted-issuer identity links.

## Optional operations connection

The Pod agent is a separate optional receiver for update, restore, and diagnostics commands. A Pod owner enables it with the exact generic issuer and Pod audience. Its signed commands have their own command type, short expiry, and durable replay protection. Enabling an operations connection does not approve an issuer for human login or grant any Pod membership.

Marketplace, billing, lifecycle, and intelligence configuration may still need external operational integration. They must use their own contracts and may not be repurposed to bootstrap user identity or membership.

## Federation routes

| Route | Purpose |
|---|---|
| `POST /api/federation/bootstrap` | Create the first local owner of a fresh managed Pod using an installer-provided Pod-local secret and generic assertion |
| `POST /api/federation/identity-links` | Create a local issuer-subject identity link from a direct Pod session |
| `POST /api/federation/identity-links/consume` | Let the issuer consume the one-time link receipt server-to-server |
| `POST /api/federation/access-grants` | Apply an issuer-authorized workspace or project membership grant |
| `POST /api/federation/exchange` | Exchange a user assertion for a Pod-local session |

All federation assertions are ES256-signed, canonical HTTPS issuer and audience bound, purpose limited, short lived, and durably replay protected. Dynamic JWKS resolution rejects local/private network and DNS-rebinding targets.

## Retired connection bridge

The following routes are retired and return an explicit retirement response. New clients must not call them or retain fallback code:

- `POST /api/handshake`
- `POST /pods/handshake` and `/pods/handshake-jwt`
- `POST /api/provision/connect`
- `POST /api/provision/seed-trust`
- `POST /api/provision/seed-admin`
