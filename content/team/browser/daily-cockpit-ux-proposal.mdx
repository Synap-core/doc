# Browser daily cockpit UX proposal

**Status:** Product/design proposal  
**Owner lens:** Product owner + UX strategy  
**Primary surface:** Electron Browser  
**Design companion:** [Browser daily cockpit design prompt](/team/design/browser-daily-cockpit-ux-design-prompt)

## One sentence

Synap Browser should become the user's daily cockpit for captured context, AI work, and decisions: a calm desktop home where the user captures anything, sees what needs attention, continues meaningful work, and trusts AI to organize the rest.

## Why this matters

Synap already has the hard part: a sovereign data pod, typed entities, relations, views, cells, proposals, channels, agents, sessions, imports, sync, search, and proactive intelligence.

The current risk is not missing capability. The risk is that users meet Synap as a collection of powerful apps instead of one clear daily experience.

The product promise is:

> Never lose anything. Never organize anything.

The current Browser should express that promise immediately. A user should not need to learn "Data", "Views", "Profiles", "Reactions", "Workflows", "Proposals", "Sessions", and "Agents" before feeling value. Those are real primitives, but they should progressively appear when they help the user's current job.

## Current product diagnosis

### Strengths

- The capture pipeline has the right mental model: raw input becomes structured proposals, with optional AI follow-up, review, execution, dedup, and fallback.
- Home is already a bento dashboard, which matches the platform philosophy that everything visual is a cell.
- Proposals and event chain give Synap a real trust model for AI mutation.
- Sessions, channels, views, and cells can compose into rich work rooms without new product silos.
- Backend capabilities already support a meaningful product loop across entities, documents, search, graph, feeds, automations, agents, and proactive AI.

### Weaknesses

- The top-level navigation exposes too many platform nouns at once.
- "Home" exists at multiple levels: pod home, workspace home, dashboard home. The distinction is important but not yet obvious.
- Proactive intelligence exists, but feels like infrastructure/settings rather than a daily source of useful suggestions.
- Reactions and proposals are architecturally strong, but the end-user language should be simpler: "Needs attention", "Activity", "What changed", "Review".
- Builder/developer surfaces are too close to first-run surfaces. Power should stay available without becoming the default first impression.

## Product principle

Synap Browser should lead with **intent and continuity**, not configuration.

Users should feel:

- "I can throw anything into this."
- "Synap knows what it became."
- "I can see what changed and what needs my decision."
- "I can continue the important work from where I left off."
- "The system is organizing itself, but I remain in control."

## Proposed top-level UX model

Replace the mental model of "many apps" with four primary lanes.

```text
Capture
  Get anything into Synap in under 3 seconds.

Today / Attention
  See what needs review, what changed, and what AI thinks matters.

Library / Spaces
  Browse durable knowledge by space, profile, view, entity, relation, and document.

Build / Automate
  Configure agents, views, cells, workflows, connectors, marketplace, and data structure.
```

These are product lanes, not necessarily four literal tabs. They should govern navigation, homepage grouping, command palette ranking, onboarding, empty states, and AI suggestions.

## Information architecture

### First-level surfaces

| Surface | User meaning | Current primitives underneath |
|---|---|---|
| Home | Daily cockpit across pod or current workspace | Bento, capture-flow, recent entities, sessions, proposals, proactive feed, activity |
| Capture | Universal input and import entry | IntakeWidget, capture pipeline, import pipeline, browser context capture |
| Attention | Decisions and useful signals | Proposals, notifications, proactive AI, event chain, session updates |
| Library | Durable knowledge and spaces | Entities, profiles, views, documents, graph, search |
| Work | Active sessions and rooms | Focus sessions, channels, agents, artifacts, outputs |
| Build | Power tools and configuration | Views, workflows, agents, cells, marketplace, data structure, connectors, settings |

### Progressive disclosure

Default rail for most users:

```text
Home
Capture
Attention
Library
Work
```

Secondary access:

```text
Build
Settings
```

Power surfaces should remain reachable through command palette, plus "Build" and contextual entry points. They should not all compete in the main rail.

## Home hierarchy

Synap needs three homes, but they must be visibly distinct.

### Pod Home

The pod-wide command center. It answers:

- What is happening across my whole life/work?
- What should I review?
- What can I continue?
- What has Synap captured recently?
- Which spaces are active?

Default content:

- universal capture input
- attention queue
- active or recent sessions
- recent captures and entities
- proactive suggestions
- workspace/space cards
- import/connectors health
- vault and sync status

### Workspace Home

A durable lens for one workspace. It answers:

- What is happening in this project/domain?
- What are the important views, entities, channels, and sessions here?
- What decisions and proposals are waiting in this workspace?

Default content:

- workspace capture input
- active sessions in workspace
- pinned views
- recent workspace entities/documents
- workspace proposals
- key dashboard cells
- members/agents

### Focus Session Home

A goal-bound work room. It answers:

- What are we trying to get done?
- Who or what is working on it?
- What changed?
- What outputs are being produced?
- What decisions need review?

Default content:

- goal and expected outputs
- channel/room stream
- session event timeline
- generated artifacts
- proposal queue
- active source/research list
- adaptive bento dashboard

## Core end-user flows

### Flow 1: First-run value

Goal: make the promise concrete within 60 seconds.

1. User opens Browser.
2. Browser asks one plain-language question: "What do you want Synap to help you remember or work on?"
3. User can choose:
   - capture a thought
   - import files
   - connect a source
   - start with a goal
4. Synap structures the first item and shows a small review.
5. The item lands in Home and Library.
6. Synap suggests one next useful action, not ten.

Success moment:

> "I gave it messy context, and now I can see usable structure."

### Flow 2: Quick capture during work

Goal: zero-to-captured in under 3 seconds.

Entry points:

- global shortcut
- Browser context menu
- Home capture cell
- command palette
- import dropzone

Experience:

1. User enters text, URL, selected page text, file, or pasted data.
2. Synap shows "capturing" with minimal interruption.
3. If confidence is high, it creates or queues review depending on policy.
4. If clarification is needed, AI asks one focused follow-up.
5. Result appears in recent captures and relevant workspace/library.

Design rule:

Capture is the primary action. Type/schema decisions are AI work, not user work.

### Flow 3: Morning return

Goal: open Synap and know what matters.

Home should show:

- "3 things need your attention"
- "2 sessions can be resumed"
- "7 captures were organized yesterday"
- "AI found 1 question emerging from recent notes"
- "One connector needs re-auth"

The user can:

- approve/reject a proposal
- resume a session
- open a suggested view
- mute a proactive suggestion
- capture something new

### Flow 4: Review AI work

Goal: governance feels calm, fast, and trustworthy.

Attention should merge:

- AI proposals
- generated view/dashboard changes
- import mapping reviews
- automation suggestions
- vault access requests
- session outputs ready for approval

Each review item needs:

- what will change
- why AI did it
- affected workspace/entities
- confidence or risk
- approve, edit, reject
- batch controls where safe

Language should be user-facing:

- "Review changes"
- "Needs attention"
- "Ready to approve"
- "Suggested by AI"

Avoid making users navigate to a generic "Proposals" app unless they are power users.

### Flow 5: Continue a work session

Goal: sessions become the durable way to do meaningful work.

User sees an active or paused session on Home:

- goal
- elapsed/last active
- active agents/humans
- current output
- proposal count
- next action

Opening it shows a session room:

- left/top: goal, outputs, participants
- center: channel + event stream
- right: selected entity/proposal/source/artifact
- bottom or side: adaptive cells/views

The session can produce:

- decision memo
- whiteboard synthesis
- dashboard
- structured entities
- CSV/table
- reusable playbook

### Flow 6: Explore the library

Goal: turn structured data into confidence.

Library should be a humane entry to the graph:

- recent entities across profiles
- spaces/workspaces
- profile sections
- saved views
- search
- relationship preview
- documents and sources

The first screen should not be "raw database." It should be "everything you captured is here, and it has shape."

### Flow 7: Build and automate

Goal: power without overwhelming.

Build is for:

- create/edit views
- agents and governance
- workflows/automations
- data structure/profiles
- cells/cell studio
- marketplace
- connectors/imports

AI should frequently offer build actions from context:

- "Create a view from these tasks"
- "Turn this repeated review into an automation"
- "Add a property to track priority"
- "Create a session template from this run"

## Design direction

The UI should feel like:

- calm desktop software
- premium, dense enough for repeated work
- warm dark-first, not generic SaaS blue
- responsive but desktop-primary
- alive through useful state changes, not decorative animation

Avoid:

- giant marketing hero screens inside the app
- decorative AI gradients
- too many cards inside cards
- exposing every internal noun at once
- making users configure schemas before they capture
- making AI feel autonomous without review

## Product copy direction

Prefer user language:

- Capture
- Needs attention
- Continue
- Library
- Spaces
- Review changes
- Suggested by AI
- Start a session
- Build

Use platform language after the user is oriented:

- entities
- profiles
- views
- cells
- proposals
- reactions
- automations
- relation types

## Alignment check

**Alignment: HIGH**

This proposal fits Synap's north star because it does not add a new product silo. It reorganizes existing primitives around clearer user jobs:

- **Emergent complexity:** Home, sessions, and library compose cells, views, entities, channels, and proposals.
- **Capture-first:** Capture remains the primary path and is visible everywhere.
- **Progressive disclosure:** Power surfaces move behind Build and contextual suggestions.
- **Human-in-the-loop:** Attention makes proposals and AI changes more visible, not less.
- **Config-over-code:** The model relies on bento configs, view configs, cells, and workspace templates.
- **Sovereignty:** The pod remains the source of truth.

## Open questions

- Should "Attention" be a visible top-level rail item, or should it live inside Home as the first section?
- Should "Work" be called "Sessions", "Work", or "Rooms"?
- Should Library merge Data + Views + Profiles in the nav, with those as internal tabs?
- How much builder power should be visible to non-technical users on day one?
- Should proactive suggestions appear as a feed, cards in Home, or a companion side panel?
- What is the minimum viable first-run experience for V0 BYO-agent users specifically?

## Recommended next step

Use the companion design prompt to generate 8 to 10 high-fidelity screens. Judge the directions against three tasks:

1. Can a new user capture something and see it become useful?
2. Can a returning user see what needs attention in under 10 seconds?
3. Can a power user still reach views, agents, automations, and data structure without the product feeling simplified into a toy?
