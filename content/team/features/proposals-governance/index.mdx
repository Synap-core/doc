# Proposals & Governance

The governance layer keeps humans in the loop when AI agents and external
connectors mutate data. Direct user mutations go through tRPC/Drizzle normally.
AI mutations and external syncs go through `checkPermissionOrPropose()`.

Proposals are part of the event chain. A proposal represents a requested mutation
that did not execute automatically because governance required review.

## Proposal flow

| Step | Description |
|------|-------------|
| **Request event** | Mutating routes emit `*.requested` with a `correlationId` before governance decides whether the action can execute. |
| **Proposal creation** | `checkPermissionOrPropose()` either grants, denies, auto-approves, or calls the canonical `createPendingProposal()` helper. Explicit approval endpoints use `createEventBackedProposal()`, which emits the requested event then delegates to `createPendingProposal()`. |
| **Proposal review** | Proposals appear in Inbox/Studio/Eve review surfaces. Users see the request summary, semantic changes, actor/target names, reasoning, and correlated event chain. |
| **Approval** | Approval emits `*.validated` with the same `correlationId`; workers/materializers apply the change and emit `*.completed`. |

## Proposal types

The proposal system manages:

| Type | Description | Auto-approved? |
|------|-------------|----------------|
| `entity_update` | AI-created entity changes | Depends on scope |
| `entity_create` | AI-generated new entities | When DEFAULT_AUTO_APPROVE applies |
| `workspace_proposal` | Multi-entity workspace changes | Always requires approval |
| `doc_proposal` | Document modifications | When DEFAULT_AUTO_APPROVE applies |
| `proactive_action` | AI-suggested structural improvements | Always requires approval |

## Governance principles

1. **Direct user mutations** → tRPC/Drizzle after normal workspace permission checks.
2. **Governed mutations** → `.requested` event → `checkPermissionOrPropose()` → grant, deny, auto-approve, or pending proposal.
3. **Explicit proposal requests** → `createEventBackedProposal()` → `.requested` event → `createPendingProposal()`.
4. **Approval** → `.validated` event → materialization → `.completed` event.
5. **Default auto-approve whitelist** → `DEFAULT_AUTO_APPROVE` config for low-risk mutations.
6. **RBAC** → Role-based access control on proposal review actions.

## Backend invariants

- Do not insert pending proposals directly in routers.
- Use `checkPermissionOrPropose()` for normal writes.
- Use `createEventBackedProposal()` only for endpoints whose job is to create a proposal directly.
- `createPendingProposal()` is the only pending-proposal insert helper and owns proposal notifications/side effects.
- Preserve `correlationId` from requested → proposal → validated → completed.
