# Trusted Issuers

> **Canonical scope (team):** Pod-local issuer approval and generic federation.
> This is not a Control Plane integration guide. See [Pod Federation Boundary](/team/control-plane/pod-trust-architecture) for the responsibility split.

## The boundary

A Data Pod owns its users, memberships, workspaces, projects, and sessions. An external service can prove facts about a person only after a Pod owner approves it as a **trusted issuer**.

The Pod persists only generic information:

| Record | Meaning |
|---|---|
| `trusted_issuers` | Approved issuer URL, lifecycle state, and capability ceiling |
| `federated_identity_links` | One opaque issuer subject mapped to one local Pod user |
| `federated_access_receipts` | Idempotency record for an issuer-authorized membership command |
| `issuer_identity_link_receipts` | One-time proof that a browser had a direct local Pod session |
| `federated_assertion_receipts` | Durable single-use receipt for a signed assertion `jti` |

The Pod does **not** persist an external account ID, an external Pod ID, a provider URL as an authentication default, or a provider-specific membership table. A standalone Pod starts with no external issuer trusted by default.

## Issuer lifecycle

```text
local owner starts approval or bootstrap
                 |
                 v
              pending ---- reject ----> rejected
                 |
                 +---- approve -----> approved ---- revoke ----> revoked
```

Only an approved issuer can use a capability. The current federation capabilities are deliberately narrow:

| Capability | Pod operation |
|---|---|
| `auth:exchange-user` | Exchange an issuer assertion for a Pod-local session after the subject is linked and has active local access |
| `identity:link-user` | Link a directly authenticated local Pod user to an issuer subject |
| `membership:grant` | Request one exact local workspace or project membership |

The capability list is a ceiling, not a grant of global authority. The Pod validates every target workspace or project and remains authoritative for its own access rules.

## Assertion contract

Federation endpoints accept short-lived ES256 JWTs with an exact canonical HTTPS `iss`, the Pod's canonical `aud`, `iat`, `exp`, and a non-empty `jti`.

1. The Pod checks issuer approval and the required capability.
2. It resolves the issuer's JWKS safely: HTTPS only, public DNS only, DNS-pinned connection, bounded response, no implicit environment fallback.
3. It verifies signature, issuer, audience, lifetime, and purpose-specific claims.
4. It consumes `(issuer_id, jti)` atomically in `federated_assertion_receipts` before a mutation or session mint.
5. It performs the local operation only if the issuer subject is linked and the Pod's own membership checks pass.

The in-process JWT replay cache is an optimization. The database receipt is the authority across restarts and API replicas.

## Generic federation routes

| Route | Caller | Purpose |
|---|---|---|
| `POST /api/federation/identity-links` | Browser with a direct Pod session | Bind one issuer subject to the authenticated local user and return an opaque receipt |
| `POST /api/federation/identity-links/consume` | Issuer server | Consume that receipt and return the Pod-authoritative access projection |
| `POST /api/federation/access-grants` | Approved issuer | Apply one exact workspace or project membership command |
| `POST /api/federation/exchange` | Browser | Exchange a user assertion directly for a Pod session |
| `POST /api/federation/bootstrap` | Installation orchestrator | Establish the first local owner with a Pod-local bootstrap secret plus a generic assertion |

The legacy user handshake and legacy provisioning identity routes return an explicit retirement response. They must not be used by new callers.

## First-owner bootstrap

An uninitialized Pod has one exceptional path: `POST /api/federation/bootstrap` accepts a locally configured installation secret in `X-Pod-Bootstrap-Token` and a normal issuer assertion with purpose `initial-owner-bootstrap`.

The secret authorizes only the first-owner operation. It is not a user credential, does not identify an issuer, and cannot create a second human owner. The resulting local owner approves the issuer with the minimum federation capabilities needed for normal exchange and membership commands.

## Operational integrations are separate

Some older marketplace, intelligence, and lifecycle integrations may still use an optional external-service URL in operational configuration. That setting is not consulted by federation identity, local user creation, membership authorization, or session exchange. It must not be treated as a trust anchor.

Those integrations are being migrated separately to provider-neutral operational contracts. Do not add new identity or membership behavior to them.
