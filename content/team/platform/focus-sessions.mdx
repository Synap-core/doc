# Focus Sessions

**Status:** product concept and UX architecture direction.

Synap has strong primitives: data pods, workspaces, entities, views, cells, channels, whiteboards, markdown documents, vault, terminal, connectors, proposals, and agents. A **focus session** is the missing user-facing layer that composes those primitives into a clear end-to-end job.

The product should not ask users to manage data structures first. It should ask:

> What are you trying to get done?

Then Synap creates or reuses the right workspace, opens a goal-bound session, starts the channel, prepares the dashboard, captures events, and helps produce the final output.

## Core Model

```text
Data Pod
  -> Workspace
    -> Focus Session
      -> Channel + Dashboard + Events + Outputs
```

## Concept Definitions

### Data Pod

The pod is the user's sovereign data universe. It is the highest-level memory and ownership boundary.

Pod-wide UX is appropriate for:

- global capture inbox
- universal search
- vault
- personal proactive feed
- installed agents, skills, connectors, and automations
- reusable people, companies, sources, files, and contacts
- cross-workspace graph and recent activity
- resume/reopen recent sessions

The pod answers:

> What does Synap know for this user?

### Workspace

A workspace is a durable context and permission boundary. It should not be created for every short task or AI thread.

A workspace should exist when there is:

- a stable project, client, company, team, or domain
- a meaningful access-control boundary
- durable views, dashboards, documents, channels, or whiteboards
- workspace-specific entity profiles or property overlays
- a lifecycle that can be archived or revisited

Examples:

- Personal
- Synap Company
- Client: ACME
- Market Research
- Fundraising
- Open Source Backend
- Sales Pipeline

The workspace answers:

> Where is this work happening, and who can participate?

### Focus Session

A focus session is a temporary, goal-bound period of work inside a workspace. It is not the same as the existing front-end surface session runtime.

A focus session includes:

- a goal
- status and progress
- one main channel
- optional branch channels
- participants: humans and agents
- a live dashboard
- generated or updated entities
- related views, cells, whiteboards, documents, and terminal outputs
- event timeline
- proposals and approvals
- final recap and outputs

The focus session answers:

> What are we trying to accomplish right now?

### Surface Session

The existing `@synap-core/surface-session` package models what is currently open in the browser shell: tabs, panels, side islands, companion context, focus history, and surface placement.

A focus session is higher-level product state. It may open many surface instances, but it is not itself a tab model.

| Concept | Owns | Example |
| --- | --- | --- |
| Workspace | Durable context, members, permissions, views, data lens | "Fundraising" |
| Focus session | Goal, event log, active work, outputs | "Find 50 seed-stage investors" |
| Surface session | Open browser surfaces and placement | table tab + channel side panel + whiteboard |
| Channel | Conversation and event stream | humans + sales agent + research agent |

## Product Principle

Users should feel they are entering a focused room around a goal, not assembling tools.

Good focus sessions feel:

- goal-oriented
- calm by default
- context-rich without being overwhelming
- AI-native but user-led
- reversible and auditable
- easy to close, recap, and return to

Bad focus sessions feel:

- like a generic chat thread
- like a temporary workspace clone
- like a dashboard full of unrelated widgets
- like the user must organize everything manually
- like AI is acting without visible intent or permission

## Lifecycle

### 1. Start

The user starts from intent:

- Research a topic
- Find leads
- Write a decision memo
- Analyze competitors
- Plan a project
- Review documents
- Investigate an incident
- Import and organize data

Synap should infer the likely workspace, or offer a lightweight choice:

- use current workspace
- use an existing workspace
- create a new workspace

The user should not need to choose a data model first.

### 2. Configure Goal

Each session should have a compact goal contract:

```yaml
goal: Find 50 qualified leads and draft a first outreach message for each.
workspaceId: sales-pipeline
expectedOutputs:
  - CSV of leads
  - outreach message drafts
  - qualification summary
successCriteria:
  - 50 leads found
  - each lead has company, role, source, reason, and confidence score
  - messages are ready for approval before sending
constraints:
  - do not send messages without approval
  - prefer EU-based companies
  - exclude existing contacts
```

This gives agents enough orientation to redirect off-topic work, propose branches, and keep the session moving.

### 3. Work

During the session, Synap composes primitives:

- **Channel** for human/AI conversation.
- **Dashboard** for progress and active widgets.
- **Views** for structured data projections.
- **Cells** for reusable cards, metrics, tables, insights, proposals, charts, and outputs.
- **Whiteboard** for synthesis and spatial thinking.
- **Markdown renderer** for memos, briefs, and living artifacts.
- **Property renderer** for generated forms and entity/property editing.
- **Vault** for governed credentials and secret requests.
- **Terminal** for power-user operations, scripts, and inspection.
- **Event chain** for traceable changes.
- **Proposals** for governed AI mutations.

### 4. Adapt

The session dashboard should evolve from what is happening.

Examples:

- If many `person` entities are created, propose a lead table widget.
- If many sources are captured, propose a source quality matrix.
- If the session has deadlines, propose a calendar/timeline cell.
- If the user repeatedly checks a profile, propose a profile activity graph.
- If many unresolved proposals exist, surface an approval queue cell.
- If two threads diverge, suggest a branch channel or a new focus session.

AI may propose dashboard updates, but meaningful writes should remain governed by the proposal system.

### 5. Close

Closing a session should produce a recap:

- goal and completion status
- key events
- entities created or updated
- sources captured
- decisions made
- proposals approved/rejected/pending
- unresolved questions
- final outputs
- suggested next sessions

The session should remain searchable and reopenable from pod-wide history and workspace history.

## Canonical Flow: Research Room

**Intent:** turn messy information into a decision memo.

1. User starts: "Research whether we should position Synap as open-source personal data infrastructure."
2. Synap creates a focus session in the relevant workspace.
3. Session opens:
   - research channel
   - live research dashboard
   - source table
   - synthesis whiteboard
   - draft markdown memo
4. User captures web pages, notes, files, and snippets.
5. AI extracts sources, claims, companies, people, risks, and open questions.
6. Dashboard updates with source count, claim clusters, contradictions, and pending actions.
7. Whiteboard spatially clusters claims and evidence.
8. Channel hosts human and agent discussion.
9. Markdown memo embeds source cards, evidence matrix, decision card, and next-action cells.
10. Session closes with final memo, linked entities, and suggested follow-up sessions.

## Canonical Flow: Lead Sprint

**Intent:** find and prepare outreach for qualified leads.

1. User starts: "Find 50 qualified leads and draft outreach messages."
2. Synap creates a goal-bound sales focus session.
3. Dashboard shows:
   - progress counter
   - lead table
   - source queue
   - quality score distribution
   - outreach draft queue
   - approval queue
4. Agents search, enrich, deduplicate, and propose lead entities.
5. User reviews proposals and edits criteria.
6. Outreach messages are drafted but not sent without approval.
7. Final outputs are a CSV, message drafts, and a session recap.

## Workspace Handling

Do not create one workspace per focus session by default.

Use this decision rule:

| User intent | Recommended scope |
| --- | --- |
| One short task within an existing project | New focus session in existing workspace |
| New durable project or team context | New workspace with first focus session |
| Personal capture or loose thought | Pod-wide capture inbox, optionally later assigned |
| Sensitive client/team separation | Separate workspace |
| New agent persona or branch | Channel or branch, not workspace |
| Reusable data across projects | Pod-wide entity profile when appropriate |

## Home And Workspace UX

### Pod Home

The browser should open to a pod-powered home when no specific workspace/session is active.

Pod home should emphasize:

- import/connect data
- recent captures
- recent sessions
- proactive feed
- global search
- global dashboard widgets
- vault/connectors status
- suggested next focus sessions
- cross-workspace highlights

### Workspace Home

Workspace home is a lens on data for a durable context.

Workspace home should emphasize:

- active focus sessions
- workspace channels
- pinned views
- workspace dashboard widgets
- recent entities and documents
- proposals and notifications
- workspace apps
- team/member activity
- AI suggestions grounded in this workspace

### Focus Session Home

Session home is the active work cockpit.

Session home should emphasize:

- goal
- progress
- main channel
- live dashboard
- active views/cells
- current outputs
- event timeline
- approvals
- next action

## AI Dashboard Composition

Dashboards are bento grids composed of cells. The user can edit them directly, and agents can propose updates.

AI should be able to propose:

- adding a widget
- removing a stale widget
- resizing/rearranging cells
- changing a view filter
- creating a new view
- embedding a view into a markdown document
- adding a whiteboard section or source cluster

Dashboard changes should be explainable:

> I noticed this session is generating many person entities, so I suggest adding a lead quality table and a source coverage chart.

## Open Questions

- Should focus sessions be first-class backend records immediately, or begin as channel metadata plus events?
- Which events define session membership: explicit session id, workspace + time window, or channel thread id?
- Can a session span multiple workspaces, or should that create a cross-workspace pod-level session?
- What is the right default session duration and idle timeout?
- Should closing a session require a recap, or can sessions remain open-ended?
- Which AI dashboard edits should auto-apply, and which require proposals?
- How should users archive, resume, duplicate, or template a session?
- Which templates should ship first: Research Room, Lead Sprint, Decision Memo, Incident Room, Import Cleanup?
- How should focus sessions appear in mobile Relay?
- How do we prevent "session sprawl" from becoming the new workspace sprawl?

## Product Validation Questions

Before implementation, validate:

- Can a new user understand the difference between pod, workspace, and session in under one minute?
- Can a user start useful work without knowing the word "workspace"?
- Does the session dashboard help the user act, or does it become another place to manage?
- Does AI feel like a collaborator in the room, not a separate chat product?
- Does every generated artifact remain reusable after the session ends?
- Does closing a session make the user feel progress was captured?
