# Surface Session Runtime

**Status:** implementation contract, package created at `@synap-core/surface-session`.

Synap has a canonical `SurfaceDescriptor` for what an app wants to open and a canonical `RendererTarget` for how that surface should render. The missing layer is the live session model: what is open now, where it lives, what is focused, how the user reached it, and what the companion is allowed to see.

`@synap-core/surface-session` owns that layer.

## Responsibility Split

| Package | Owns | Does not own |
| --- | --- | --- |
| `@synap-core/surface-runtime` | Surface intent: entity, view, document, app, artifact, requested placement. | Live tabs, focus, breadcrumbs, host state. |
| `@synap-core/renderer-runtime` | Renderer resolution: cell, view, profile/entity, iframe-srcdoc, external app. | Window placement or shell behavior. |
| `@synap-core/surface-session` | Live opened surfaces, placement stacks, active focus, user journey trails, companion context snapshots. | React state implementation, persistence policy, rendering. |
| `@synap-core/cell-runtime` | Content rendering once a cell target is chosen. | Shell layout, global tabs, companion context. |
| `@synap-core/spatial-shell` | Reusable Browser V2 visual primitives. | Product state, routing, data loading. |

This keeps the separation clean:

- **container** = surface session and host placement
- **content** = renderer target and cell/view/profile/iframe rendering

## Core Model

### SurfaceInstance

A `SurfaceInstance` is a live opened instance of a `SurfaceDescriptor`.

It includes:

- `id` and stable `key`
- original `surface`
- current `placement`
- optional `rendererTarget`
- status and attention state
- origin metadata
- per-instance trail
- companion-visible context metadata
- local host state
- timestamps

The same entity may exist as two surface instances if the host disables dedupe, but the default is to dedupe by `surfaceKey(surface)`.

### SurfaceTrailItem

The trail is the breadcrumb model.

It is intentionally **not** a backend hierarchy. It is the user's path through the product:

- Home → Q2 Pipeline → Helix Robotics
- Documents → Q1 Board Memo → Helix Robotics
- Search → Helix Robotics
- Companion → Proposal Draft → Helix Robotics

Those are all valid trails for the same entity. The active tab's trail powers the header breadcrumb, and the companion receives the focused trail in its context snapshot.

### SurfaceSessionState

`SurfaceSessionState` is the host-agnostic front-end session truth.

It stores:

- all open `surfaces`
- placement stacks for `main`, `side`, `companion`, `floating`, `modal`, `popover`, `embed`, and `fullscreen`
- floating frame geometry
- active surface id
- focus history
- workspace id

Browser, web, and Eve can store this state in different host stores. The package only provides pure TypeScript operations.

### SurfaceContextMetadata

Context metadata is the host's compact description of a surface for AI and shell UI.

It includes:

- `workspaceId`
- `appId`
- resource type/id
- `profileSlug`
- title/subtitle/summary
- current selection
- companion visibility
- companion role: `primary`, `context`, `source`, `tool`, or `hidden`
- tags and extra metadata

This is how the companion knows what is open without importing app UI or scraping DOM.

### SurfaceContextSnapshot

`buildSurfaceContextSnapshot(state)` produces the AI-facing view of the session:

- active surface
- focused trail
- visible surfaces
- open resources
- current selection

The companion should consume this snapshot. It should not depend on Browser-specific tab state, CRM internals, or document-specific UI.

## Host Integration Pattern

Every host should follow this flow:

1. Receive `openSurface(surface, options)`.
2. Resolve renderer target using `@synap-core/renderer-runtime`.
3. Derive trail from the active surface when opening child/context surfaces.
4. Call `openSurfaceInstance(sessionState, { surface, rendererTarget, placement, trail, context })`.
5. Render placement stacks with the host's shell.
6. Feed `buildSurfaceContextSnapshot(sessionState)` to the companion.

Compatibility wrappers stay thin:

- `openPanel(...)` creates a surface and calls `openSurface(...)`.
- `openCellPanel(...)` creates a cell surface and calls `openSurface(...)`.
- `openSidePanelTab(...)` creates a surface and calls `openSurface(...)`.
- route navigation creates or focuses a main surface.

## Browser V2 Integration

Browser V2 should make `@synap-core/surface-session` the live state spine behind the spatial shell.

Recommended sequence:

1. Keep old Browser store stable.
2. Add a Browser adapter that owns one `SurfaceSessionState` per workspace/window.
3. Dual-write existing Browser tab and side-panel actions into the session.
4. Render Browser V2 from `session.placements` instead of static demo surfaces.
5. Move breadcrumbs to `getSurfaceTrail(session, activeSurfaceId)`.
6. Feed companion from `buildSurfaceContextSnapshot(session)`.
7. Replace old tab/panel logic with wrappers once V2 behavior matches V1.

The old Browser tab model is still useful as implementation experience. It should become host adapter behavior, not the platform contract.

## Placement Semantics

| Placement slot | Meaning |
| --- | --- |
| `main` | Primary tabbed work island. |
| `side` | Optional resizable side island for any surface. |
| `companion` | Global guided-work companion island. |
| `floating` | Temporary spatial panel behind feature flag. |
| `modal` | Blocking focused task. |
| `popover` | Anchored transient detail. |
| `embed` | Surface rendered inside another surface. |
| `fullscreen` | Expanded focus mode for a selected island. |

`surface-runtime` currently exposes host-neutral placements. `surface-session` adds `companion` and `fullscreen` as host session slots because those are shell states, not generic open intents.

## Metadata Rules

Surface metadata must be enough for AI and host UI to understand the user task without importing feature code.

Use:

- `surface.title` for direct UI labels
- `surface.rendererHint` for explicit renderer intent
- `surface.source` for low-level source host/app/request
- `SurfaceOrigin` for user journey origin
- `SurfaceTrailItem[]` for breadcrumb history
- `SurfaceContextMetadata` for AI-visible compact state
- `rendererTarget` for the chosen rendering path

Do not store:

- full document contents unless the surface is an artifact with explicit content
- credentials or secrets
- arbitrary app store snapshots
- backend mutation intent without proposal governance

## Persistence

V1 should persist only minimal local session shape, if needed:

- surface descriptors
- placement stacks
- active id
- trail labels and surface keys
- non-sensitive context metadata
- floating geometry

Do not persist renderer component state or AI hidden reasoning. Backend persistence can come later if it becomes part of workspace/session collaboration.

## Validation Checklist

Before Browser V2 replaces the old shell, validate:

- Opening entity/view/document/channel/app/artifact creates a `SurfaceInstance`.
- Main, side, companion, and floating placements work from the same data model.
- The same entity can show different breadcrumbs depending on origin.
- Companion context updates when focus changes.
- Hidden surfaces are excluded from normal companion snapshots.
- Existing Browser V1 wrappers still behave the same.
- Renderer resolution remains metadata-based and does not require schema migration.

## Future Direction

Once Browser V2 stabilizes:

- web can adopt the same state model for compatibility
- Eve can map session placements to panes/companions/srcdoc apps
- generated iframe apps can become normal app or artifact surfaces
- profile/entity rendering can plug in through `@synap-core/profile-renderer`
- package/capability visibility can become a surface instead of global chrome
