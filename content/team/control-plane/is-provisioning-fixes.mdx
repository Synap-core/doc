# IS Provisioning — Retired CP Identity Flow

> **Historical record — do not implement.** This page previously described a Control Plane-specific `provisionJwt` flow. It was removed because it let an external account service write its Pod identity and made multi-Pod behaviour unsafe.

## What was retired

The old design used a CP-signed `provisionJwt`, `podId`, and `controlPlane` settings pushed to a Pod through `/api/provision/connect`. It also described Hub-side forwarding of that JWT. Those routes and behaviours are retired:

- `POST /api/provision/connect`
- `POST /api/provision/seed-trust`
- `POST /api/provision/seed-admin`
- `POST /api/handshake`

They return an explicit retirement response and must not be restored to repair intelligence provisioning, tier propagation, or a reconnect action.

## Current boundary

The Data Pod owns local users, memberships, workspaces, projects, and sessions. The Control Plane owns its own account/session state, invitations, and its ledger of Pod relationships. It can never use an intelligence operation to write a Control Plane user ID, Pod ID, or issuer configuration into the Pod identity model.

The supported account-to-Pod routes are generic federation routes:

| Route | Purpose |
|---|---|
| `/api/federation/bootstrap` | Create the first local owner of a fresh managed Pod with a Pod-local installer secret |
| `/api/federation/identity-links` and `/consume` | Prove existing direct Pod access and record a relationship receipt |
| `/api/federation/access-grants` | Apply a scoped local membership grant after Pod verification |
| `/api/federation/exchange` | Exchange a short-lived issuer assertion directly for a Pod session |

The Intelligence Hub uses Hub Protocol credentials, not a user federation assertion or retired provisioning token. Any remaining marketplace, billing, lifecycle, or intelligence-delivery integration needs a separate provider-neutral operations contract; it cannot be smuggled through federation identity state.
