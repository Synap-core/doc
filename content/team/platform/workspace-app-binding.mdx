## Overview

Every Synap app (CRM, Canvas, DevPlane) operates against a **dedicated workspace** on the user's pod. The workspace scopes views, settings, and workspace-scoped entities to that app's domain. A CRM workspace holds pipeline views and CRM-specific layouts; a DevPlane workspace holds apps, packages, and deployment targets.

**Studio is pod-wide, not workspace-wide.** Studio's workspace exists for settings and view storage, but Studio's core data (notes, documents, people) uses `entityScope: 'pod'` — entities are visible across all apps and workspaces. Studio does not gate its data behind a workspace boundary.

The key invariant: **one workspace per app per user** (today). Multi-workspace per app is a planned capability.

## How App Workspaces Are Created

### 1. The `proposalId` — app identity key

Every app defines a stable string that identifies "my workspace type":

| App | proposalId |
|-----|-----------|
| CRM | `crm-personal-v1` |
| Studio | `studio-personal-v1` |
| Canvas | `canvas-personal-v1` |
| DevPlane | `builder-workspace-v1` |

This string is passed to `trpc.workspaces.createFromDefinition` on first launch. The backend stamps it into `workspace.settings.proposalId` and uses it as an **idempotency key** — calling `createFromDefinition` with the same `proposalId` for the same user always returns the same workspace, never creates a duplicate.

### 2. Boot sequence (`useWorkspaceSetup`)

All apps (except DevPlane which has a bespoke hook) use the shared `useWorkspaceSetup` hook from `@synap-core/auth-hooks`:

```
1. Fetch workspaces.list (all user workspaces)
2. Check localStorage cache (key: "<app>-workspace-id:<userId>")
   → validate cached ID still exists in the list
3. Search list for workspace where settings.proposalId === this app's proposalId
4. Legacy name fallback (legacyName param, e.g. "CRM", "My Studio") for pre-proposalId workspaces
5a. If nothing found AND query succeeded AND user has OTHER workspaces → "needs-picker" phase
5b. If nothing found AND query succeeded AND user has NO workspaces → createFromDefinition → new workspace
6. Store resolved ID in scoped localStorage key
7. Call updateWorkspaceId() → injects X-Workspace-Id header into all tRPC calls
```

The localStorage key is **scoped to userId** (`<app>-workspace-id:<userId>`) to prevent cross-identity contamination when the same browser has been used by multiple Kratos identities (e.g., authing through Studio vs. directly through CRM).

#### `needs-picker` phase

When a user has workspaces but none match by `proposalId` or `legacyName` (e.g., an invited user who has access to workspaces created before the `proposalId` stamp was introduced), `useWorkspaceSetup` enters a `"needs-picker"` phase instead of auto-creating. The hook surfaces:

```ts
{
  phase: "needs-picker",
  availableWorkspaces: Workspace[],
  selectWorkspace: (id: string) => void,
  createNew: () => void,
}
```

The caller (e.g., `useCrmSetup`) can show a workspace picker UI. The user either selects an existing workspace or triggers `createNew()` to run the normal `createFromDefinition` path.

`useCrmSetup` passes `legacyName: "CRM"` to catch workspaces created before the `proposalId` stamp. This prevents the `needs-picker` phase from firing for users who have a CRM workspace that was named "CRM" before the proposalId convention existed.

### 3. `createFromDefinition` on the backend

The procedure (`workspaces.ts`) accepts:

```typescript
{
  definition: WorkspaceProposal   // profiles, views, channels, bentoLayout
  proposalId: string              // e.g. "crm-personal-v1"
  workspaceType: "personal"       // always "personal" for app workspaces today
  workspaceName: string           // e.g. "CRM"
}
```

On success it stamps `settings.proposalId` into the workspace row. Concurrent calls with the same `(userId, proposalId)` are serialized via a distributed lock — no races, no duplicates.

## What the Backend Enforces

| Guard | Enforced | Notes |
|-------|----------|-------|
| User membership (`workspace_members`) | ✅ Always | Every workspace read/write checks the user is a member |
| `proposalId` idempotency on creation | ✅ Always | Same app can't create duplicate workspaces |
| Workspace belongs to calling app | ❌ Not enforced | Any valid workspace ID in `X-Workspace-Id` is accepted |
| `workspaces.list` filtered by app | ❌ Not enforced | Returns all user workspaces regardless of type |
| `settings.appId` populated | ❌ Not used | Field exists in schema but is never written |

The backend trusts the frontend to send the right workspace ID. The only hard gate is membership.

## Current Gaps

### Gap 1 — `workspaces.list` returns everything

Every app calls `workspaces.list` at boot to find its workspace. That call returns **all** user workspaces: CRM's, Studio's, Canvas's, DevPlane's, agent workspaces, etc. The app then searches the full list for `settings.proposalId === "crm-personal-v1"`.

This is correct but wasteful, and it means each app has visibility into the full workspace inventory of the user.

### Gap 2 — No app-to-workspace binding on the backend

If a bug or a malicious request sends a CRM workspace ID to a Studio API call, the backend will process it happily as long as the user is a member. There is no validation that workspace `499328b7-...` is a CRM workspace and therefore should not be accessible from Studio's tRPC context.

In practice this is low risk today (all apps are same-origin, same user), but it's an architectural hole worth closing.

### Gap 3 — One workspace per app is enforced implicitly

The `proposalId` idempotency means there's exactly one CRM workspace per user. If a user wants a second CRM workspace (e.g., one for personal clients, one for a side business), there's no way to do it — the second `createFromDefinition` call just returns the first one.

### Gap 4 — `settings.appId` field exists but is never written

`WorkspaceSettings` has `appId?: string` defined but no app ever populates it. Right now `proposalId` does double-duty as both the idempotency key and the app identifier. These two concerns should be separated.

## Hardening Roadmap

### Phase 1 — Stamp `appId` and filter `list` (no schema migration needed)

**Backend changes** (`workspaces.ts`):

1. When `createFromDefinition` is called, extract `appId` from the definition object (or from a new input field) and stamp it into `settings.appId`.
2. Add an optional `appId` filter to `workspaces.list`:

```typescript
list: protectedProcedure
  .input(z.object({
    appId: z.string().optional(),       // ← new
    includeArchived: z.boolean().default(false),
  }).optional())
  .query(async ({ ctx, input }) => {
    // ... existing membership query ...
    return memberships.filter(m => {
      if (!input?.appId) return true;   // no filter = return all (backward compat)
      const s = (m.workspace?.settings ?? {}) as Record<string, unknown>;
      return s.appId === input.appId;
    });
  })
```

**Frontend changes** (`useWorkspaceSetup` + each app's setup hook):

Pass `appId` to the workspace definition and to `listWorkspaces()`:

```typescript
// crm/lib/useCrmSetup.ts
const listWorkspaces = useCallback(async () => {
  const data = await utils.workspaces.list.fetch({ appId: "crm" });
  // ...
}, [utils]);
```

This means CRM only ever sees CRM workspaces in its list, and the `proposalId` lookup is just a secondary verification.

**Impact:** Zero migration needed. Existing workspaces without `settings.appId` are returned only when no filter is passed (backward compatible). New workspaces get `appId` stamped automatically.

### Phase 2 — Multi-workspace per app

Once apps filter `list` by `appId`, the `proposalId` no longer needs to be the uniqueness key. Instead:

- `proposalId` becomes a **template identifier**: `"crm-personal-v1"` describes the _shape_ (which profiles and views to create), not the _instance_.
- Remove idempotency by `proposalId` for apps that opt into multi-workspace (pass `allowMultiple: true` to `createFromDefinition`).
- The frontend sidebar's workspace switcher (planned in `@synap-core/app-shell`) shows all workspaces for the current app, filtered by `appId`.
- "New workspace" button in the switcher calls `createFromDefinition` with a user-supplied name.

**Naming the difference:**
```
proposalId "crm-personal-v1"  →  "I want a workspace shaped like CRM"
appId "crm"                   →  "this workspace belongs to the CRM app"
workspaceName "Personal Sales" →  user-visible display name
```

### Phase 3 — Backend app-context validation (optional, future)

For strict isolation, `workspaceProcedure` could accept an `expectedAppId` and validate:

```typescript
const settings = (workspace.settings ?? {}) as WorkspaceSettings;
if (expectedAppId && settings.appId && settings.appId !== expectedAppId) {
  throw new TRPCError({ code: "FORBIDDEN", message: "Workspace app mismatch" });
}
```

This prevents cross-app workspace ID injection. Low priority until multi-tenant features arrive.

## Data Sharing Across Workspaces

Some entities have `entityScope: 'pod'` — they're visible in **all workspaces** by design (person, company, deal, task, event, note). This is the intended cross-app data layer.

For example: a contact added in CRM is a pod-scoped `person` entity. The same entity appears in Studio's People view. This is not a bug — it's the core data model.

Workspace-scoped entities (`entityScope: 'workspace'`) are private to their workspace. A CRM deal is not visible in Studio's entity list.

**What this means for workspace switching:**
- Pod-scoped data "follows" the user across all workspaces — switching from CRM workspace A to CRM workspace B doesn't lose contacts.
- Workspace-scoped data (custom profiles, CRM-specific views, pipeline configs) stays in the workspace it was created in.
- Users switching workspaces within the same app will see the same people/companies but different pipeline views.

## Shared Sidebar Package

The workspace switcher is being consolidated into a shared `@synap-core/app-shell` package (see `packages/core/app-shell/PLAN.md`). The `SidebarUserMenu` component will accept:

```typescript
{
  lsCacheKeyBase: string  // e.g. "crm-workspace-id"
  proposalId: string      // e.g. "crm-personal-v1"
  // future: appId for Phase 1 list filtering
}
```

It queries `workspaces.list` filtered to the current app and renders a "Switch workspace" section when multiple workspaces exist. Once Phase 1 lands, this will use `appId` instead of (or in addition to) `proposalId` matching.
