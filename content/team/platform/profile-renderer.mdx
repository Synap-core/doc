# Profile Renderer — Two Slots, Two Paths

**Status:** North Star (architecture locked 2026-05-19, infrastructure in progress).
**Audience:** anyone building entity surfaces (CRM, Studio, Browser, Eve OS, package authors, AI agents that emit UIs).

## TL;DR

Any entity, in any profile, in any workspace, can be opened to a renderer chosen by the user, the workspace owner, or AI. Renderers are pluggable, AI-extendable, file-uploadable, and resolved at runtime. The product becomes self-generating: new apps emerge from data + configuration, not code deploys.

The system has exactly two axes:

- **Two slots per profile** — *list* (open a profile, see all its entities) and *detail* (open one entity).
- **Two paths per renderer** — *config* (typed, safe, replicable) and *file* (sandboxed, custom, escape hatch).

That's 2×2. Everything else is consequence.

## Why two slots

Every well-tested platform that solves "render my data type X" separates these slots:

- Notion: database views (list) vs page templates (detail)
- Airtable: views (list) vs interfaces (detail)
- Anytype: sets/collections (list) vs object layouts (detail)

The slots are not interchangeable. A kanban makes sense for *all* tasks; a kanban renderer for *one* task is incoherent. Conflating them was Salesforce's first mistake.

## Why two paths (not three)

The natural temptation is to split renderers by origin: built-in, AI-generated, user-uploaded. That's wrong. Origin is a *producer* concern, not a *substance* concern.

The real distinction — the one that lines up with security, cacheability, indexability, and contract stability — is **interpreted config vs untrusted code**:

| Path       | What it is                                                | Security                                        | Producer                                 |
| ---------- | --------------------------------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| **Config** | A `rendererKey` + typed config object, interpreted by trusted host code | Safe — host owns execution                      | Built-in registry, AI, user (via picker) |
| **File**   | A sandboxed iframe bundle that uses the Pod SDK           | Sandbox + capability manifest + proposal gating | User, AI, package author                 |

AI is a producer that can target either path. So is the user (via the picker). So is a package author (via templates shipped with their workspace package). The substance — config or file — is what determines security, storage, and lifecycle.

This breaks the v0/Lovable failure mode: once an AI emits a renderer, it lives as a normal `RendererRef`. The next edit is a property change (config path) or a fresh proposal (file path) — not a regeneration spiral that loses context.

## The 2×2

|                | **Config path** (safe, typed, replicable)                                                       | **File path** (sandboxed, custom, escape hatch)                                |
| -------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **List slot**  | Registered list renderer + typed config (`kanban` / `table` / `list` / `calendar` / `gallery` / `graph` / `timeline` / `gantt` / `matrix` / `map` / `bento`) | Sandboxed iframe file that renders all entities of a profile via the Pod SDK   |
| **Detail slot**| Registered detail renderer + typed config (`form` / `document` / `dashboard` / `comment-thread`) | Sandboxed iframe file that renders one entity via the Pod SDK                  |

## Storage

Two columns, one settings overlay. No new tables for the renderers themselves — built-in renderers live in code (registered as cells in `cellRegistry`), generated configs are inline JSONB, file-path renderers reuse the existing `iframe-srcdoc` / `external-app` kinds and live in `widget_definitions`.

`RendererRef` is an **alias of the existing `RendererTarget`** from `@synap-core/renderer-runtime`. There is no new discriminated union — the two paths are already encoded in `RendererTarget.kind`:

```ts
// from @synap-core/renderer-runtime — re-exported as RendererRef by profile-renderer
type RendererTarget =
  | { kind: 'cell';          cellKey: string; props: Record<string, unknown>; /* … */ }   // config path (registered)
  | { kind: 'view';          viewId: string;  /* … */ }                                    // config path (saved view)
  | { kind: 'iframe-srcdoc'; appId: string;   srcdoc: string; /* … */ }                    // file path (inline bundle)
  | { kind: 'external-app';  appId: string;   url: string;    /* … */ }                    // file path (pod-served URL)
  | { kind: 'url';           url: string;     /* … */ };
```

Capability manifest, integrity hash, and SDK version pinning attach to file-path renderers as a **Phase 3 hardening layer** above this basic shape — see "File-path security" below.

Inside `workspaces.settings` (existing JSONB column — no migration needed for the overlay itself, just a new key):

```ts
interface WorkspaceSettings {

  profileRenderers?: Record<string, {
    list?: RendererRef;
    detail?: RendererRef;

```

Mirrors how `profileBentoViewIds` already lives in `settings`. Same merge-on-update semantics (`z.record`).

`schema-coherence.ts` gains two entries under `profiles`:

```ts

```

## Resolver

The single rendering rule. Mirrors `getEffectiveProperties` exactly.

```ts
// synap-backend/packages/database/src/services/profile-resolution-service.ts

async getEffectiveRenderer(
  profileSlug: string,
  workspaceId: string | null,
  slot: 'list' | 'detail',
): Promise<RendererRef> {
  // 1. workspace overlay
  if (workspaceId) {
    const workspace = await this.workspaces.get(workspaceId);
    const overlay = workspace?.settings?.profileRenderers?.[profileSlug]?.[slot];
    if (overlay) return overlay;
  }

  // 2. profile default
  const profile = await this.profiles.getBySlug(profileSlug, workspaceId);
  const defaultRef = slot === 'list'
    ? profile?.defaultListRenderer
    : profile?.defaultDetailRenderer;
  if (defaultRef) return defaultRef;

  // 3. system fallback — keeps the system bootable when no profile config exists.
  //    Returns RendererTarget shapes (kind: 'cell') backed by existing registered cells.
  return slot === 'list'
    ? { kind: 'cell', cellKey: 'list',          props: {} }
    : { kind: 'cell', cellKey: 'entity-detail', props: {} };
}
```

```
GET /api/hub/profiles/{slug}/renderers?workspaceId=...
```

### `@synap-core/profile-renderer`

Shipped 2026-05-19 as Phase 1 infrastructure. ~140 LOC. Source-direct (no build step), depends only on `@synap-core/renderer-runtime` + `@synap-core/surface-runtime` + React.

**Public surface:**

```ts
// types.ts
export type ProfileRendererSlot = 'list' | 'detail';

// RendererRef is an alias of RendererTarget — no new union.
export type RendererRef = RendererTarget;

export interface ProfileRendererContext {
  profileSlug: string;
  workspaceId: string | null;
  slot: ProfileRendererSlot;
  entityId?: string;
}

// Caller-injected. Real implementations: tRPC, Hub Protocol REST, mock for tests.
export type ProfileRendererResolver = (
  ctx: ProfileRendererContext,
) => Promise<RendererRef | null>;

export type ProfileRendererState =
  | { status: 'loading' }
  | { status: 'resolved'; target: RendererRef }
  | { status: 'not-found' }
  | { status: 'error'; error: Error };
```

```tsx
// EntityRenderer.tsx — the single host every app mounts
export interface EntityRendererProps {
  profileSlug: string;
  workspaceId: string | null;
  entityId?: string;                                   // omit → list slot, provide → detail
  resolve: ProfileRendererResolver;                    // injected data source
  renderTarget: (target: RendererRef) => ReactNode;    // injected renderer
  fallback?: ReactNode;
  empty?: ReactNode;
  errorFallback?: (error: Error) => ReactNode;
}

export function EntityRenderer({ /* … */ }) {
  const slot: ProfileRendererSlot = entityId ? 'detail' : 'list';
  const state = useResolvedRenderer({ profileSlug, workspaceId, slot, entityId }, resolve);

  if (state.status === 'loading') return fallback;
  if (state.status === 'error') return errorFallback ? errorFallback(state.error) : empty;
  if (state.status === 'not-found') return empty;
  return renderTarget(state.target);
}
```

**Why `resolve` and `renderTarget` are injected, not built-in:**

- **`resolve`** depends on the data source (tRPC, Hub Protocol, mock). Injecting keeps the package dependency-light below `renderer-runtime` + `surface-runtime`.
- **`renderTarget`** depends on host capabilities. Cell rendering needs `@synap-core/cell-runtime`'s `CellRenderer`; iframe-srcdoc rendering needs a sandbox host; URL rendering needs a router. Apps choose which kinds they support.

The package owns the slot semantics and the resolver state machine — nothing else. Existing primitives do the heavy lifting.

### `@synap-core/pod-sdk`

The contract for code running *inside* a sandboxed renderer. Stable surface: every breaking change bumps `sdkVersion`. Files pin a major.

```ts
// Identity & workspace
export function useUser(): User;
export function useWorkspace(): Workspace | null;

// Data
export function usePodQuery<T>(key: PodQueryKey, input: unknown): UseQueryResult<T>;
export function usePodMutation<T, V>(key: PodMutationKey): UseMutationResult<T, V>;

// Entity-shaped helpers
export function useEntity(id: string): UseQueryResult<Entity>;
export function useEntities(filter: EntityFilter): UseQueryResult<Entity[]>;
export function useProfile(slug: string): UseQueryResult<Profile>;
export function useEffectiveProperties(profileId: string): UseQueryResult<EffectiveProperty[]>;

// UI primitives — pre-themed, theme tokens live in CSS variables propagated via postMessage handshake
export * from './ui';   // re-exports HeroUI components + Synap-themed wrappers
export { theme } from './theme';
```

**Dual backend.** A build-time switch selects:

- *In-host mode* — the SDK calls tRPC directly via the existing client. Used by built-in renderers running in the main bundle.
- *In-sandbox mode* — every SDK call serializes to a postMessage envelope, sent to the parent window, the parent's tRPC client makes the actual call, the result is returned. Used by file-path renderers.

The two modes share types and hook signatures. Renderer authors write code once.

### Sandbox host — Phase 3 hardening above existing iframe support

File-path rendering does **not** ship in `@synap-core/profile-renderer`. The existing `renderer-runtime` resolver already returns `kind: 'iframe-srcdoc'` and `kind: 'external-app'`, and apps already know how to mount iframes for those kinds (e.g., `IframeCustomWidget` in the bento widget surface).

Phase 3 adds a **hardened iframe host** that sits on top of those existing kinds when the source is an AI-generated or user-uploaded renderer bundle:

```tsx
// Phase 3 — not in profile-renderer; likely a sibling package or extension of cell-runtime
function SandboxedRendererHost({ fileRef, manifest, ... }) {
  // 1. Verify manifest signature + integrity
  // 2. Check requested capabilities → granted vs proposal-gated
  // 3. Mount <iframe sandbox="allow-scripts"> served from same-origin pod
  // 4. postMessage handshake: send user, workspace, entity, theme tokens, granted capabilities
  // 5. Bridge SDK calls: child → parent envelope → parent's tRPC client → reply
  // 6. Capability denial → proposal flow (existing checkPermissionOrPropose path)
}
```

Files served from `${podUrl}/renderer-assets/{fileRef}` (same-origin sandboxed iframe is the secure pattern — never external URLs). Files cannot escape the iframe, cannot reach the host DOM, cannot touch cookies directly, cannot reach the file system. All data flows through the postMessage bridge.

For Phase 1, profile-renderer's `renderTarget` callback returns whatever the host app does today for iframe-srcdoc — no hardening, no SDK bridge. Phase 3 adds those layers without changing the storage shape.

## AI generation (deferred wiring, documented now)

AI is a producer of `RendererRef`. It is not a third storage kind.

### Contract

```ts
interface RendererGenerationRequest {
  prompt: string;
  profileSlug: string;
  workspaceId: string;
  slot: 'list' | 'detail';
  // Pre-filled context the host injects, not the user:
  context: {
    propertyDefs: EffectiveProperty[];
    sampleEntities: Entity[];
    workspaceTheme: ThemeTokens;
    availableRenderers: ProfileRendererDef[];  // catalog AI can pick from
  };
}

type RendererGenerationResult =
  | { kind: 'config'; ref: RendererRef; reasoning: string }
  | { kind: 'file';   ref: RendererRef; reasoning: string; codePreview: string };
```

### Rules the AI is given (in the system prompt)

1. **Prefer config.** A `{kind:'config', rendererKey: 'kanban', config: {...}}` is always preferred over a file. Files are only emitted when the user explicitly asks for something not expressible in any existing renderer's config.
2. **Bind to real fields.** Generated configs must reference property defs from the provided context. Never invent fields.
3. **One candidate per request.** No regeneration spirals — if the user wants iteration, they accept this candidate then request changes. Each iteration is a *new candidate the user accepts or rejects*, not an in-place mutation. (Lessons from v0/Lovable.)
4. **Files must use the Pod SDK.** Generated code uses `@synap-core/pod-sdk` for all auth, data, and UI. The AI is given the SDK reference docs as context.

### Storage of AI output

A `RendererRef` produced by AI is stored identically to one produced by a human picker. No `source` discriminator on the storage; if traceability matters, the `manifest.author` field on file-path refs and an audit log entry capture it.

## File-path security (deferred wiring, documented now)

### What is enforced

- iframe with `sandbox="allow-scripts"` only — no `allow-same-origin`, no `allow-forms`, no `allow-top-navigation`
- Served from `${podUrl}/renderer-assets/{fileRef}` — same-origin to the pod, but the sandbox attribute strips ambient authority
- All data via postMessage envelope; no direct DOM, no direct cookies, no direct file system, no direct network beyond what the SDK proxies
- Manifest declares `requiredCapabilities`; anything beyond the default set (read own profile, read own entities, read theme) flows through `checkPermissionOrPropose()` exactly like every other AI mutation
- Bundle hash verified on serve; bundle pinned per `fileRef`

### What is NOT supported

- Node-level access (the Obsidian Templater anti-pattern)
- Loading from external URLs
- Importing arbitrary npm packages at runtime — files bundle their dependencies or use the SDK's re-exports
- Cross-iframe communication outside the bridge

## Picker UI (deferred wiring, documented now)

A Notion-style "Change view" affordance lives on every profile and entity surface. Three tabs, one storage shape underneath:

| Tab        | What the user sees                                                                                                | What gets persisted          |
| ---------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| Built-in   | Grid of `cellRegistry` entries tagged as profile renderers (via cell metadata), filtered by applicable profiles. Click → pick → optional config form | `RendererTarget { kind: 'cell', cellKey, props }` |
| Ask AI     | Prompt box with pre-filled context (profile name, property defs, sample). Submit → AI returns a candidate → user accepts/rejects | `RendererTarget` (any kind) |
| Add file   | Upload bundle + manifest. Capability manifest reviewed. Proposal-gated for non-default capabilities                | `RendererTarget { kind: 'iframe-srcdoc' \| 'external-app' }` |

The picker writes either to the profile default (admin-only) or to the workspace overlay (workspace member). Per-user overrides are explicitly out of scope until/unless there's user demand.

## Migration plan

1. **Browser canary.** Universal routes `/entity/:profileSlug` (list) and `/entity/:profileSlug/:id` (detail) mount `<EntityRenderer>`. Ship with 3 config-path list renderers reusing existing view adapters (`kanban`, `table`, `list`) and 2 config-path detail renderers (`form`, `document`). File path is stubbed but the resolver wires through. Proves the model end-to-end.

2. **CRM.** Migrate the four hardcoded detail pages one at a time: contacts → companies → deals → clients. Each migration replaces ~500–700 lines of bespoke layout with `<EntityRenderer>` + a registered detail renderer. Bespoke CRM logic moves into the renderer's component or into cells composed inside it.

3. **Studio.** Replace `EntityRenderer` dispatch and profile-specific overrides with calls to the new resolver. Studio's `GenericEntityView` becomes the `form` detail renderer; existing overrides become per-profile defaults via `profiles.default_detail_renderer`.

4. **Eve OS.** Adopts the same package. Eve's `/data/[id]` route becomes the universal pattern, with workspace context flowing through scope. Manual `HeroField` building in Eve is replaced by the `form` renderer's standard rendering.

## Anti-goals

Explicitly NOT in scope. Each was tempting, and each is the wrong direction:

- **Salesforce-style assignment matrix** (`App × RecordType × Profile × FormFactor`). Two axes, that's all.
- **Two parallel paradigms** for the same job (Airtable's views vs interfaces). One `RendererRef`, two paths, two slots.
- **Per-user renderer overrides.** Workspace is the unit, like the sidebar. Per-user can land later if real demand surfaces.
- **AI as a separate storage kind.** AI produces config or file; the storage doesn't care who made it.
- **Trusted JS execution** (Obsidian Templater model). All file-path code runs sandboxed.
- **Mixing cells and renderers in one registry.** Cells = sub-page units. Renderers = page-level. Conflating made the previous model fuzzy.
- **AI regeneration loops** (v0/Lovable). Each AI generation is a new candidate, not a mutation.
- **External URLs for renderer files.** Same-origin pod-served only.

## Open questions

1. **Where do file-path bundles live?** Extend `widget_definitions` (which already has iframe widgets) vs. a new `renderer_files` table vs. `assets` with a `kind: 'renderer-bundle'` discriminator. Decision deferred to Phase 3.
2. **SDK versioning policy.** Major-pin per file vs. compatibility ranges. Lean toward strict major-pin to avoid breakage.
3. **Renderer marketplace?** Package authors can ship renderers; how do they get distributed beyond the bundled set? Out of scope for now; design must not preclude.
4. **Per-entity override.** Browser today has `entity.systemData.bentoViewId` — an entity-level override. Should this survive as a third resolution layer (entity → workspace overlay → profile default → fallback)? Provisional answer: yes, kept for ad-hoc override but not surfaced in the picker until Phase 3.
5. **Workspace package templates.** Workspace packages (CRM, Project Management, etc.) want to ship `profileRenderers` defaults in their template JSON. Templates already provision profiles, views, bento; this adds one field per profile.

## Why this changes the product

Today, building a new app on Synap means: write profile + write views + write workspace template + write a bespoke detail page somewhere in the app code. The bespoke page is the friction point — it requires a code deploy and an app team.

With this North Star: profile + property defs + renderer choices. All data. All editable in the workspace. All AI-generatable. A new "app" is a workspace template that picks the right renderers for its profiles. The Browser (and Eve) become universal entity surfaces — they don't care what the data looks like, the resolver tells them. Apps become data, not deploys.

That's the self-generating product. This doc is the contract.
