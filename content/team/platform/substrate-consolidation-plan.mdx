# Substrate Consolidation Plan — Current → Homoiconic

*Synap Technologies — Version 0.1, June 2026*
*Execution plan for [The Homoiconic Substrate](/team/home/homoiconic-substrate) via [The Universal Node](/team/platform/universal-node-schema). Grounded in verified backend state.*

---

## How to read this plan

> **Execution status (June 2026):** the backend-only governance + cleanup + hardening slice of this plan is being executed **first and separately** as the [AI Governance & Foundations Hardening Plan](/team/platform/governance-hardening-plan) — work that's valuable now regardless of the refactor and that de-risks it. The heavy, frontend-touching phases below (esp. **Phase 2 cell merge** and **Phase 5 reflective UI**) and the new-capability **Phase 1** are **deferred** until those foundations land. As hardening items complete, they're struck through in both docs.

This is the bridge from **what the code is today** to **what the white paper describes**. It is deliberately honest: every "current state" was verified by direct code reading (see the white paper's Evidence Index), and every target is justified by a single test:

> **The Deletion Test.** A consolidation step is real only if it lets us *delete* a table, a column, a registry, or a hand-sync. If a change adds a layer without removing one, it is decoration — reject it.

The work is **consolidation, not invention** (white paper §5): the substrate already exists scattered across the codebase; we are unifying it, not building it from zero. That is why this is tractable rather than a multi-year compiler project.

**The governing sequencing principle: envelope-first, merge-later.** We never big-bang a table merge. We introduce the shared abstraction (the `NodeEnvelope`, a shared policy module, an atom registry) as *additive, non-breaking* changes first, migrate kinds behind it one at a time, and only collapse physical tables once every consumer reads through the abstraction. This keeps every wave shippable and reversible.

## Invariants — what must NOT break (read before any wave)

These are load-bearing properties of the live system. Every wave preserves them or it does not ship.

1. **The governance membrane stays total.** No change may let an AI write reach the DB without passing `checkPermissionOrPropose()`. The surface language stays **total / non-Turing-complete** so proposals remain inspectable (white paper §5). *Decidability and governance-by-construction are the same property — do not trade it away for expressiveness.*
2. **Three-layer data discipline.** `hooks → stores → client → backend → DB`. Never skip, never import upward (`.claude/rules/frontend-rules.md`).
3. **Migration discipline is strict** (`.claude/rules/backend-rules.md`): schema changes land *only* via hand-written, numbered `.sql` files in `packages/database/migrations/`, written defensively (`IF NOT EXISTS`). `drizzle-kit push/generate` are forbidden. **Every new column/table must also be added to `0000_baseline_schema.sql` and registered in `schema-coherence.ts`** or the pod refuses to boot.
4. **Hub Protocol is the only external boundary.** All IS/external-agent traffic stays on `/api/hub/*` REST. No tRPC at the wire.
5. **`agentType` ⊥ `intelligenceServiceId`.** Never add per-agent or per-channel IS routing (`.claude/rules/intelligence-rules.md`).
6. **No data loss.** Table merges run as *backfill + dual-read + cutover + drop*, never *drop-then-recreate*. The event spine is the recovery backstop.

## Phase 0 — No-regret foundations

Three additive changes. None breaks a consumer. Each is valuable even if the rest of the plan slipped.

### 0a — Extract one governance policy ✅ DONE *(roadmap #5; details in [Governance Hardening Plan](/team/platform/governance-hardening-plan) Wave A)*
- **Current.** `checkPermissionOrPropose` (in `@synap/api`) is the canonical gate, but `@synap/jobs/src/utils/automation-governance.ts` is a **hand-copied mirror** of its `DEFAULT_AUTO_APPROVE` / `ADMIN_ACTIONS` / precedence ladder (a circular-dependency workaround). Self-documented drift risk: the two whitelists can silently diverge.
- **Target.** One policy module in a lower package (e.g. `@synap/governance-policy`) that both `api` and `jobs` import.
- **Create.** The shared package: policy constants + the pure decision function (no DB).
- **Consolidate.** Point both call sites at it.
- **Delete.** `automation-governance.ts`'s forked constants. ✅ *Deletion test passes.*
- **Risk.** Low. Pure refactor; behavior-preserving. **Gate:** a test asserting the jobs path and the api path produce identical decisions for a matrix of (action, role, issuer, mode).

### 0b — Introduce the `NodeEnvelope` as a shared type *(U1, enables #2, #4)*
- **Current.** Identity/ownership/trust/provenance/version/soft-delete are re-declared on `profiles`, `views`, `widget_definitions`, `cell_instances`, `channels`, and `users`-as-agent — partially and inconsistently (`trustLevel` on two tables; `createdByKind` on one; `scope` modeled differently per table).
- **Target.** One `NodeEnvelope` TypeScript type + a documented column set (§2 of the schema spec) that every node-bearing table conforms to. **Additive only** in Phase 0 — we add missing columns (`createdByKind`, `createdByUserId`, `agentUserId`, `sourceProposalId`, `trustLevel`) where absent, defaulted, behind `IF NOT EXISTS`.
- **Create.** The shared type; defensive migrations adding the missing envelope columns; `schema-coherence.ts` + `0000_baseline_schema.sql` updates.
- **Consolidate.** Repositories read/write the envelope through one helper.
- **Delete.** Nothing yet (deletion lands in Phases 2–3 when tables merge). *This is the enabling step, not the payoff.*
- **Risk.** Low–medium (touches many tables, but additive). **Gate:** every node-bearing table has the full envelope; typecheck + pod boots (schema-coherence passes).

### 0c — Enumerate and publish the Atom Registry *(U3, roadmap #3)*
- **Current.** The finite code-backed vocabulary is real but scattered and uncounted: renderer atoms in `@synap/capabilities`, 12 flow-node atoms in `schema/automations.ts`, tool atoms in IS `tool-categories.ts`, kernel-op atoms in `permission-check.ts`. No single catalog; no per-atom `configSchema` used for AI validation.
- **Target.** One `AtomRegistry` (§4 of the schema spec): `{ atomKey, atomClass, configSchema, trustLevel:'trusted', deps }`, generated/collected from the existing sources. Publish the **count** (this is the measurable answer to "can it build any app").
- **Create.** The registry + a per-atom JSON Schema. Wire the schema into the AI authoring repair loop (agent emits node → validate against atom configSchema → errors feed repair).
- **Consolidate.** `CAPABILITIES_MANIFEST` becomes the *renderer-atom slice* of this registry (sets up Phase 2's kill of the hand-sync).
- **Delete.** Nothing yet; sets up deletions in Phase 2.
- **Risk.** Low. Mostly collection + codegen. **Gate:** every `typeKey` used by any live node resolves to a registry atom; orphans reported (not silently dropped).

## Phase 1 — Bring behavior into the definition JSON *(roadmap #1 — highest leverage)*

This is the change that turns *"JSON → skeleton"* into *"JSON → living application."* It is first among the heavy work because its leverage is highest and its dependencies are lowest.

- **Current.** `createWorkspaceFromDefinition()` is a real, idempotent, resumable 11-step pipeline — but its `WorkspaceDefinition` schema has **no `automations`, `channels`, or `commands` keys**, and none of the 4 shipped templates contain them. Automations exist as a full system (`flowDefinition` = nodes+edges, 12 node types) created through a *separate* router. So a generated workspace has structure and surfaces but **no wired behavior**.
- **Target.** `WorkspaceDefinition` gains `automations[]`, `channels[]`, `commands[]`. The pipeline gains steps 12–14 that instantiate them by calling the *existing* automations/channels/commands routers (not new logic — wiring). A single JSON now produces a workspace with schema + views + layout + seed data + **behavior**.
- **Create.** Zod schema extensions; pipeline steps 12–14 (idempotent, resumable, same `completedSteps` pattern); cross-reference validation (an automation's trigger profile must exist; a channel's member agent must resolve). One reference template (e.g. extend `agent-os.json`) that ships a working automation + an `agent_collab` channel.
- **Consolidate.** The definition becomes the single source for a workspace's full behavior, not just its shape.
- **Fix.** Resolve the ordering: automations/channels reference profiles, views, *and* (for agent members) agent identities — sequence them after those steps, with `ref:` resolution like seed entities already use.
- **Delete.** Bespoke per-template setup scripts that wire behavior outside the definition, if any. *Deletion test: a workspace's behavior is no longer set up by anything but its definition.*
- **Risk.** Medium. New instantiation paths; must stay idempotent/resumable. **Gate:** instantiate the reference template on a clean pod → the automation fires on its trigger and the agent_collab channel has its members — verified live (dogfood), not just typecheck.

> **Note:** This phase is *cleaner* if `automation`/`channel`/`agent` are already `NodeKind`s (Phase 0b), because the definition becomes "a bundle of nodes" uniformly — but it does **not** require the full Universal Node. It can ship by extending the existing importer. Do it now; refactor onto nodes in Phase 2–3.

## Phase 2 — Universal Node: the surface plane *(roadmap #2 — the cell merge)*

The largest schema consolidation. Envelope-first, merge-later.

- **Current.** Three overlapping "renderable unit" tables: `widget_definitions` (cell *types*), `cell_instances` (placed cells), `views` (saved collection-renderers). Plus `CAPABILITIES_MANIFEST` hand-synced into `widget_definitions` at boot (drifts silently if the manifest isn't rebuilt). A "cell" is sometimes a `widget_definitions` row, sometimes a `cell_instances` row; a "view" overlaps both.
- **Target.** One logical `cell`-kind node (§3.2 of the schema spec): a **cell type** = system-scoped cell node (carries `configSchema`); a **cell instance** = workspace-scoped cell node; a **view** = a cell instance whose body carries `scopeProfileIds` + `query`. One render path (`CellRenderer`), differentiated by whether the body has a query. *This makes "Views are already cells" structural — reconciling the two North Stars (see schema spec §0).*
- **Create.** A `cell` node body conforming to the envelope (0b); a backfill that maps the three tables into it; dual-read adapters so consumers keep working during cutover.
- **Consolidate.** `CAPABILITIES_MANIFEST` → seeds **system cell-type nodes** directly (via the Atom Registry, 0c). The boot-time `seed-widget-definitions` reconciliation becomes a node seed.
- **Fix.** The `views` table's deprecated duplicate columns (`filter`/`sort`/`columns`/`layoutConfig` vs `query`/`config`/`scopeProfileIds`) — finish that in-flight migration as part of the merge, not separately.
- **Delete.** `widget_definitions` and `cell_instances` tables (merged into cell nodes); the `CAPABILITIES_MANIFEST ↔ widget_definitions` hand-sync; the deprecated view columns. ✅ *Strong deletion test — three tables/one sync removed.*
- **Risk.** **High.** This is the heavy one — touches the renderer, the cell registry, bento composition, and the frontend `cell-runtime`. **Mitigation:** logical envelope + dual-read first (ship behind a read adapter), physical table drop last, one kind-slice at a time (widget-defs → cell-types first; then cell_instances; then views). **Gate:** the UI Gallery (`apps/ui-gallery`, :5599) and the browser render every existing cell/view identically pre- and post-merge — visual diff verified live (Playwright/chrome-devtools MCP), per the visual-QA discipline.

## Phase 3 — Actor plane: identity + durable spawn *(roadmap #4)*

- **Current.** Agent identity is split: a `users` row (`userType:'agent'`, the runtime identity), a separate `agents` catalog table (`intelligenceServiceId`, `capabilities`, `slug`), and `agent_configs` (overrides). The migration that "promoted" agent fields to real `users` columns still **dual-writes** `agentMetadata` for back-compat. `parentAgentId` exists but **no code writes it** — runtime spawn (`dispatch_agent`) is ephemeral/in-process, leaving no durable lineage. `agent.create` is an `ADMIN_ACTION` (always proposal-gated).
- **Target.** Agent identity unified under `kind:'agent'`: an **agent definition** (was `agents` catalog + `agent_configs`) = system/workspace-scoped agent node; an **agent instance** = the `users` row (kept, for auth). `parentAgentId` becomes a real relation between agent nodes, enabling **governed durable spawn**: an agent proposes the creation of a *persistent* sub-agent, a human approves (ADMIN gate preserved), lineage is recorded.
- **Create.** Agent-node body (0b envelope + AgentBody); a durable-spawn path (`dispatch_agent` mode that, on approval, materializes a persistent child agent node with `parentAgentId`).
- **Consolidate.** `agents` catalog + `agent_configs` → agent-definition nodes. Finish the dual-write migration (single source: the columns/node, drop `agentMetadata` duplication).
- **Fix.** The two-store split; the dead `agents/specialist/*.ts` classes (registry never instantiates them — either delete or document as reference).
- **Delete.** The `agents` catalog table; the `agentMetadata` dual-write; dead specialist classes. ✅ *Deletion test passes.*
- **Risk.** Medium–high (identity is security-sensitive; API keys reference `users`). **Mitigation:** keep the `users` row as the auth anchor untouched; consolidate only the *definition/config* side. **Gate:** existing agents authenticate and run unchanged; a governed durable-spawn creates a child with correct `parentAgentId` and the child's writes attribute correctly.

## Phase 4 — Transport + membrane hardening *(roadmap #6, #7)*

Two independent hardening tasks; can run alongside Phase 3.

### 4a — Unify channel membership *(roadmap #6)*
- **Current.** `group` channels use the modern typed `channel_members` table (human/agent uniform, per-member `canDraft/canPropose/canAct`); `agent_collab` still uses a legacy `metadata.participants: string[]` JSONB array. Membership is not uniform across the 7 channel types.
- **Target.** All channel types use `channel_members`.
- **Create.** A backfill from `metadata.participants` → `channel_members` rows; update the A2AI post/poll paths to read membership from the table.
- **Delete.** The `metadata.participants` read path. ✅
- **Risk.** Low–medium. **Gate:** A2AI post/poll + join-proposal behavior identical pre/post; the membrane reads the same capability grants for all channel types.

### 4b — Tighten auto-approve + durable audit *(roadmap #7)*
- **Current.** The default `DEFAULT_AUTO_APPROVE` whitelist lets routine agent creates/updates execute immediately (audited after the fact). The audit-row and event-spine writes are best-effort (`.catch(()=>{})`), so traceability is a strong tendency, not an invariant. There is no generic proposal-undo.
- **Target.** Auto-approve becomes an **explicit, per-workspace policy** (already partially exists via `aiGovernance.autoApproveFor`) with a clear default, surfaced in workspace settings — not a silent global default. Audit + the `.requested`/`.completed` spine append become **transactional with the mutation** they describe. Add a generic, best-effort `revert(proposalId)` built on the stored replayable envelope + soft-delete/versioning.
- **Create.** Policy surfacing UI/setting; transactional audit write; a generic revert path (per-subject where possible).
- **Fix.** The `.catch(()=>{})` best-effort audit; the per-subject-only reversibility.
- **Risk.** Medium (transactional audit can affect write latency; measure). **Gate:** an auto-approved write with a forced audit failure now *rolls back or surfaces*, never silently succeeds unaudited; revert of a create soft-deletes the created node.

> **Deliberate non-goal:** we are *not* removing auto-approve. Routine, reversible writes auto-approving is a correct UX trade-off; we are making it *explicit and audited*, not *forbidden*. The membrane stays strict where it matters (destructive/admin/untrusted) and honestly-labeled where it's permissive.

## Phase 5 — Reflective closure *(roadmap #8 — the payoff)*

- **Current.** Agent and automation authoring surfaces are bespoke UI. The substrate does not yet render its own authoring tools.
- **Target.** The agent-composition and automation surfaces are **cells over agent/automation nodes** — the tool that builds the system is built *by* the system (white paper §4). An "agent org chart" is a view (a cell with a query) over `kind:'agent'` nodes; an automation editor is a cell over an `automation` node. Once `automation`/`agent` are nodes (Phases 1–3) and cells are universal (Phase 2), this is *composition, not new code*.
- **Create.** Cell renderers for agent/automation/channel nodes (these are new **atoms** — added via governed proposal, per the rule).
- **Consolidate.** The Builder's living-architecture graph (already inside Synap) and these authoring cells become the same surface: Synap modeling and authoring Synap.
- **Delete.** Bespoke agent/automation authoring UI replaced by cell composition.
- **Risk.** Medium (it's product UX, verified by dogfood). **Gate:** an agent can be created/edited entirely through a cell over agent nodes; the loop closes — the substrate authors itself.

## Honest assessment of scope and risk

- **This is a multi-quarter program, not a sprint.** Phase 0 + Phase 1 are achievable near-term and deliver most of the *visible* value ("one JSON → a working app with behavior"). Phases 2–3 are the heavy, higher-risk consolidations and should be sequenced behind solid visual/dogfood gates.
- **The biggest risk is Phase 2 (cell merge).** It touches the most consumers. The envelope-first/dual-read/merge-last discipline is non-negotiable there.
- **The biggest philosophical risk is over-unification** — collapsing distinctions that should stay distinct (cells vs views was *almost* such a trap; we kept them as one kind with a typed difference, not a flattened bag). Re-read the schema spec's open decisions (§7) before each phase and surface them to the founder.
- **What this is NOT:** a rewrite. Every phase ships on the existing runtime; the layers stay as the compilation target. We are making the *surface language* uniform and bringing *behavior* and *agents* into it — not replacing the engine.
