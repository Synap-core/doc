## Data flow

```
React component
  → lib/devplane/hooks.ts         (useDevplaneEntities, useCreateDevplaneEntity…)
      → @synap-core/client        (tRPC + TanStack Query)
          → Next.js /trpc proxy
              → Synap backend pod :4000/trpc
                  → Drizzle ORM → PostgreSQL
```

Components never call tRPC directly — always through a hook in `lib/devplane/hooks.ts`. This is the three-layer rule.

## Provider tree

Split into two tiers. The first tier (in `app/providers.tsx`) is always active. The second tier (in `app/(app)/layout.tsx`) only mounts after workspace readiness is confirmed.

```
providers.tsx (always active):
  NextThemesProvider
    HeroUIProvider
      SynapProvider              ← auth context
        AppStoresSync            ← Zustand hydration
          AppTRPCProvider        ← tRPC client
            RegistryBoot
              CellRuntimeWrapper
                CommandPaletteProvider
                  {children}

app/(app)/layout.tsx (gated — only when state === "ready"):
  AppSocketProvider              ← Socket.IO → pod
    RealtimeBridge               ← cache invalidation via socket events
      AppShell + page content
```

**Why Socket.IO is gated:** tRPC requests go through the Next.js `/trpc` proxy, but Socket.IO connects directly to the pod URL (e.g. `antoine-perso.synap.live`). Connecting before the workspace is confirmed ready produces cross-origin WebSocket errors with no benefit. The readiness gate ensures Socket.IO only connects once the app is fully operational.

## Startup state machine

`hooks/useWorkspaceReadiness.ts` runs inside `WorkspaceReadinessGate` before any app content renders.

```
idle
  → no workspace in localStorage  → no_workspace → redirect /onboarding
  → workspace found               → checking

checking  (fetching profiles.list)
  → all 13 profiles present       → ready ✓
  → profiles missing, first time  → bootstrapping

bootstrapping  (createFromDefinition with existing workspaceId)
  → done                          → rechecking

rechecking  (fetching profiles.list again)
  → all 13 profiles present       → ready ✓
  → still missing                 → waiting

waiting  (scheduled retry every 3.5s)
  → profiles appear               → ready ✓
  → after 4 retries               → show "Check again" button
  → manual retry                  → reset bootstrappedRef → checking
```

Key invariants:
- `bootstrappedRef` prevents calling `createFromDefinition` more than once per mount
- Manual retry resets `bootstrappedRef` so re-bootstrap is possible
- `mountedRef` guards all state updates to prevent stale-closure updates after unmount
- `createFromDefinition` is idempotent — safe to call with an existing `workspaceId`

## WebSocket endpoints

Both connect directly to the pod (not via the Next.js proxy). The session token is passed as a query param because cookies don't transfer on cross-origin WebSocket upgrades.

### SSH Terminal — `/api/devplane/ssh`

```
?envId=<entity_id>&token=<kratos_session_token>

1. Validate token via Kratos
2. Fetch devplane_environment → envHost, sshUser, sshKeyVaultRef
3. Resolve vault://uuid → plaintext SSH key (server-side only)
4. ssh2.shell() → PTY proxy

Client → Server:  binary (input) | JSON { type:"resize", cols, rows }
Server → Client:  binary (output) | JSON { type:"ready"|"error"|"closed" }
```

### Recipe Runner — `/api/devplane/recipe-run`

```
?recipeId=<entity_id>&envId=<entity_id>&token=<kratos_session_token>

1. Validate token
2. Fetch recipe → parse recipeSteps JSON
3. Fetch environment → resolve SSH credentials
4. For each step: ssh2.exec() → stream stdout/stderr
5. Save devplane_recipe_run entity

Server → Client (JSON events):
  { type: "step_start", index, name, command }
  { type: "output", index, data }
  { type: "step_done", index, exitCode, success }
  { type: "recipe_done", success, duration }

Client → Server:  { type: "cancel" }
```

## Entity relationship graph

```
App
 ├── features      → Feature[]         (by feature.linkedApp)
 ├── services      → Service[]         (by service.linkedApp)
 ├── packages      → Package[]         (by package.consumedByApps)
 ├── deployedOn    → Server[]          (by server.linkedAppSlug)
 ├── deployments   → Deployment[]      (by deployment.linkedApp)
 ├── incidents     → Incident[]        (by incident.affectedApps)
 └── entityChannelId → AI channel

Server (devplane_environment)
 ├── envType       staging | production | local | development
 ├── kamalRole     web | worker | db | cache | all
 ├── host          IP address or hostname
 ├── sshKeyVaultRef → Vault (plaintext key never stored)
 └── linkedAppSlug → primary App

Package
 ├── dependsOn     → Package[] (comma-separated names — graph edges)
 ├── consumedByApps → App[] (comma-separated app names)
 └── health        healthScore (0–100), healthGrade (A–F), staleStatus
```

## Infrastructure model

Canonical deployment stack (provider-agnostic, SSH-based):

```
Local (dev)
  └── pnpm dev — no SSH, no DevPlane management needed

Staging (1 server)
  └── Any SSH-accessible VPS (Hetzner CX21, DO Droplet, etc.)
  └── Server entity: { envType: "staging", kamalRole: "all" }
  └── Recipe: kamal template → kamal deploy --destination staging

Production (fleet)
  └── Multiple servers with explicit roles:
      web ×N    → { kamalRole: "web" }
      worker ×N → { kamalRole: "worker" }
      db ×1     → { kamalRole: "db" }
  └── DevPlane graph view visualizes topology + live status
```

Recipe templates: `kamal` (primary), `shell`, `custom`. Docker Compose and git-pull are custom recipes.

## Design decisions

**Frontend owns profiles.** The pod/backend has no knowledge of DevPlane-specific profiles. `BUILDER_WORKSPACE_DEFINITION` is the source of truth. The old `ensureDevplaneProfiles()` in `synap-backend` is dead code — wrong scope (system vs workspace), never called.

**Idempotent bootstrap.** `createFromDefinition` with an existing `workspaceId` adds missing profiles without touching existing ones. This means the readiness gate can repair workspaces created before new profiles were added to the definition — no manual migration needed.

**Server ≠ Environment tier.** `devplane_environment` entities represent individual server nodes, not environment tiers. `envType` (staging/production) is a property, not the entity type. Multiple Server entities can share `envType: "production"` with different `kamalRole` values — this is how the Kamal fleet is modelled.

**SSH over CI.** Many self-hosted setups don't have a CI runner. SSH is the lowest common denominator and Kamal specifically expects it.

**Recipe steps as JSON string.** Synap property values are typed scalars. `JSON.stringify(steps)` keeps the data in the property system without schema changes.

**Provider-agnostic servers.** `serverProvider` is metadata only — DevPlane connects via SSH regardless of provider. Hetzner, DO, AWS, bare metal — same SSH + vault pattern.

**Full-page auth overlay.** Unauthenticated users see a full-page login overlay, not an inline login inside the app shell. This avoids rendering the app shell with broken data and gives a clean auth experience.

**tRPC 401 → session clear.** When tRPC returns 401, the `AppTRPCProvider` clears the session and redirects to `/login`. No stale auth state.

**Socket.IO gated behind readiness.** Socket.IO connects directly to the pod (not via Next.js proxy). It only mounts after workspace readiness is confirmed to avoid cross-origin WebSocket errors.

**Stories vs Features.** Stories are user-facing scenarios that orchestrate features and drive the AI pipeline. Features are individual work items with their own AI channels. A story can link to multiple features and packages.
