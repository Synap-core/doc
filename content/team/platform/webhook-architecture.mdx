# Webhook Architecture

## Overview

All inbound webhooks from third-party providers are handled under a single unified surface: `POST /api/webhooks/:provider`. There is **one mount point**, one auth model per provider, and every write flows through the service layer that calls `emitSideEffects()` — giving webhooks the same event chain as any direct API mutation.

```
External provider
       │
       ▼
POST /api/webhooks/{provider}        ← single unified path
       │
       ├── Signature verification    ← timing-safe, per-provider
       │
       ├── Parse event               ← per-provider adapter
       │
       └── Service layer write
              │
              └── emitSideEffects()
                     ├── pg-boss: automation-trigger-match
                     ├── pg-boss: search-index
                     ├── pg-boss: webhook-delivery
                     └── pg-boss: entity-embedding
```

## Registered providers

| Path | Provider | Auth method | Events handled |
|---|---|---|---|
| `/api/webhooks/messaging` | Unipile | Static header (`unipile-auth`, timing-safe) | `message.created`, `account.created`, `account.reconnection_required`, `account.disconnected` |
| `/api/webhooks/n8n` | N8N | Static secret (`X-Webhook-Secret`, timing-safe) | `inbox_item.received` |
| `/api/webhooks/kratos` | Ory Kratos | Static secret (`X-Webhook-Secret`, timing-safe) | `identity.updated` |
| `/api/webhooks/intelligence` | Intelligence Service | Bearer token (`INTELLIGENCE_SERVICE_API_KEY`, timing-safe) | `inbox_item.analyzed` |

Connector sync is a separate path, not part of this general webhook surface: the Nango webhook lands on the **Control Plane** (HMAC-verified — the CP is the sole Nango broker), which pokes the pod's `POST /api/connectors/sync-trigger` to run the sync door. See [Connectors](../crm/connectors.mdx).

## Security model

Every provider uses **timing-safe comparison** (`crypto.timingSafeEqual` with byte-length pre-check) to prevent timing attacks on secret comparison. The patterns:

- **Static header**: Unipile sends a fixed `unipile-auth` header value — checked with `timingSafeEqual`.
- **Static secret in header**: N8N and Kratos send `X-Webhook-Secret` — checked with `timingSafeEqual`.
- **Bearer token**: IS sends `Authorization: Bearer <key>` — checked with `timingSafeEqual`.

Auth failure always returns `401`. Parse failure always returns `200` (prevents retry storms from providers that retry on non-2xx).

## Event chain integration

Webhook handlers do **not** call `db.insert`/`db.update` directly. All writes go through service-layer functions that call `emitSideEffects()`:

| Write | Service | Side-effect event type |
|---|---|---|
| Messaging account upsert | `MessagingAccountService.upsert()` | `messaging_account.created.completed` |
| Messaging account status update | `MessagingAccountService.updateStatus()` | `messaging_account.disconnected.completed` / `messaging_account.reconnection_required.completed` |
| External channel creation | inline in `webhooks-inbound.ts` | `external_channel.created.completed` |
| Inbound message storage | inline in `webhooks-inbound.ts` | `external_message.received.completed` |
| Inbox item ingestion (N8N) | direct `emitSideEffects` | `inbox_item.received.completed` |
| IS analysis callback | direct `emitSideEffects` | `inbox_item.analyzed.completed` |
| Kratos identity update | `syncUserFromKratos()` + `emitSideEffects` | `user.updated.completed` |

All of these event types are defined in `packages/events/src/event-types.ts` under `OperationalEventTypes`. Automations can subscribe to any of them via `eventPattern`.

## External service connections (pod-admin managed)

Beyond the provider-specific inbound webhook surface above, pods also have a **generic external connections layer** managed from pod-admin. This is separate from the provider-specific handlers above.

### Inbound webhook for external services

Generic inbound endpoint for external services to push events into Synap:

```
POST /api/webhooks/inbound/{keyId}
Authorization: Bearer {apiKey}
Content-Type: application/json

{
  "event": "string (event type)",
  "payload": "object (free-form, delivered as-is to automations)",
  "timestamp": "ISO datetime (optional)"
}
```

**Key differences from provider-specific handlers:**

| Aspect | Provider-specific (`/api/webhooks/{provider}`) | Generic inbound (`/api/webhooks/inbound/{keyId}`) |
|---|---|---|
| **Auth** | Static header/secret per provider | Bearer token (API key lookup by keyId) |
| **Event parsing** | Per-provider adapter normalizes to canonical event | Raw passthrough — payload delivered as-is |
| **Automation trigger** | Provider-specific event type (e.g., `external_message.received`) | Generic `external_webhook.received` event |
| **Use case** | Unipile, Kratos, N8N integrations | Arbitrary external services, custom events |

### Authentication

The inbound endpoint uses **API key authentication**:

1. Extract Bearer token from `Authorization: Bearer {key}` header
2. Look up API key by `{keyId}` from URL path
3. Verify Bearer token matches the key (timing-safe comparison)
4. Check workspace isolation: if key has `workspaceId`, enforce via `X-Workspace-Id` header
5. Emit `external_webhook.received` event via `emitSideEffects`
6. Return `200 OK`

**Note**: The URL path contains the keyId, not a subscription ID. This allows flexible routing — the same API key can be shared across multiple external services (rare but possible).

### Event chain integration

Inbound webhook events flow through the same automation pipeline:

| Write | Side-effect event type |
|---|---|
| Generic inbound webhook received | `external_webhook.received.completed` |

Automations can trigger on `external_webhook.received` and filter by the `event` field:

```json
{
  "triggerType": "event",
  "triggerConfig": {
    "eventPattern": "external_webhook.received.completed",
    "filters": { "event": "custom.lead_scored" }
  }
}
```

### Workspace isolation

Inbound webhook keys are **workspace-scoped**. The middleware enforces this at the authentication layer.

## Adding a new provider

1. Create a handler file in `apps/api/src/webhooks/{provider}.ts`.
2. Implement timing-safe auth verification at the top of the handler.
3. Parse the webhook payload with a Zod schema.
4. For each event type, call the relevant service layer function — never write to `db` directly.
5. Ensure the service calls `emitSideEffects()` with `workspaceId` so automations can trigger.
6. Add the new event type constant to `OperationalEventTypes` in `event-types.ts`.
7. Mount the new router in `apps/api/src/index.ts` under `/api/webhooks/{provider}`.
8. Register the webhook URL with the provider.

## What was NOT migrated (intentionally)

`eventRepository.append()` / `createSynapEvent()` is still used in:
- `hub-utils.ts` — audit trail for Hub Protocol operations
- `events.ts`, `content.ts`, `system.ts` — explicit event log writes for internal operations

These are **not webhook handlers** — they write to the `events` table as an audit log, independent of the automation side-effect chain. This is the intended dual-use: `events` table = durable audit log; `emitSideEffects` = automation/search/delivery fan-out.
