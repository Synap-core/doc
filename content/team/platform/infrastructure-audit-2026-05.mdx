| Repo | Package / Port | Role |
|------|---------------|------|
| `synap-backend/` | `synap-backend` / 4000 | Data Pod: entities, events, Hub Protocol REST, tRPC, jobs |

## 2. Backend (synap-backend)

### 2.1 Transport Layer

Two parallel API surfaces co-exist on the same process (port 4000):

| Surface | Protocol | Auth | Used by |
|---------|----------|------|---------|
| `/trpc/*` | tRPC 11 (Hono adapter) | Kratos cookie (operator session) | Frontend apps |
| `/api/hub/*` | Hub Protocol REST (Hono) | Bearer API key | Intelligence Service, external agents |

**Critical rules:**
- Hub Protocol is NOT mounted in tRPC. It is a separate Hono router at `/api/hub/*`.
- `/api/pod/*` = user-context calls forwarded with Kratos cookie.
- `/api/hub/*` = service-context calls with `pod.agentApiKey`.
- Never mix these two auth patterns on the same endpoint.

### 2.2 Event Chain (Primary Mutation Path)

Every state change goes through the event chain — this is the architectural north star for data integrity.

```
Client/Agent → POST /api/hub/events  (or tRPC mutation)
                    ↓
          EventLog table (PostgreSQL)
                    ↓
          pg-boss workers pick up events
                    ↓
          Workers dispatch to:
            - Entity service (entity:created, entity:updated, etc.)
            - Document service
            - Relation service
            - Notification service
            - Proactive intelligence worker
```

**Subject types**: `entity | relation | user | system | workspace | project | task | document | chat | message | apiKey | member`

All 13 event types are stored with full context (who, what, why, when). This enables:
- Time travel (reconstruct any entity state at any point)
- Surgical undo (reverse one specific mutation without losing subsequent state)
- Full provenance (every field change has an author, timestamp, and rationale)
- AI feedback loop (agents learn from their own proposal acceptance/rejection rates)

### 2.3 Proposal System (AI Safety Gate)

Every AI write operation goes through `checkPermissionOrPropose()`:

```
AI tool call → checkPermissionOrPropose()
                    ↓
           RBAC check + DEFAULT_AUTO_APPROVE whitelist
           + per-workspace override
                    ↓
        accept → write immediately
        propose → create Proposal record (user reviews in UI)
        refuse → error returned to agent
```

This is load-bearing architecture, not a feature toggle. Agents are never bypassed. Every write is traceable.

### 2.4 pg-boss Workers

27 workers + 3 proactive cron jobs. Key workers:

| Worker | Trigger | Purpose |
|--------|---------|---------|
| `entity-event-worker` | entity events | Downstream entity sync |
| `notification-worker` | any event | Fan-out to notification center |
| `proactive-morning-briefing` | cron 07:00 | AI morning summary post |
| `proactive-weekly-digest` | cron Monday | Weekly insight digest |
| `proactive-health-check` | cron 6h | System health post |
| `connector-sync-worker` | schedule | Connection sync runner (`runConnectionSync`, CP-brokered) — see [Connectors](../crm/connectors.mdx) |

### 2.5 Database Schema Conventions

- **Migrations**: Hand-written `.sql` files in `packages/database/migrations/`, sorted alphabetically, one-pass. `drizzle-kit generate` and `drizzle-kit push` are FORBIDDEN.
- **Three mandatory changes** when adding a column: (1) migration file, (2) `0000_baseline_schema.sql` with `IF NOT EXISTS`, (3) `schema-coherence.ts` `REQUIRED_COLUMNS`.
- **`documents.entityId` was REMOVED** — reverse lookup: `entities WHERE documentId = ?`.
- **Drizzle enum**: use TypeScript enum value, not string literal.
- **Hono routes**: static BEFORE `/:id` dynamic routes.

## 3. Intelligence Service (synap-intelligence-service)

### 3.1 Agent Architecture

Two agent types — this is the complete canonical list:

| Type | Key | Tools | Use case |
|------|-----|-------|---------|
| `OrchestratorAgent` | `"meta"` (default) | Full tool suite (22+ tools) | General requests, coordination, co-founder AI |
| `PersonaAgent` | domain string (e.g. `"cto"`) | Branch-only tools | Domain expert (CTO, Marketing, PM, Sales) |

**Resolution rules:**
- `agentType` and `intelligenceServiceId` are **orthogonal** — never add per-agent or per-channel IS routing.
- Unknown `agentType` → OrchestratorAgent + warning (never crash).
- IS resolution: capability-first → workspace default → env fallback.

### 3.2 Tool Suite (22+ tools)

Tools live in `apps/intelligence-hub/src/tools/` grouped by category:

- **Entity tools**: create, read, update, delete, search, list profiles
- **Document tools**: create, read, update documents
- **Memory tools**: store fact, search facts (pgvector semantic search)
- **Graph tools**: query relations, traverse graph, find connected entities
- **Workspace tools**: list workspaces, get bento schema, list views
- **Action tools**: create proposal, approve proposal, post to channel

All tools communicate with the backend exclusively via Hub Protocol REST (`/api/hub/*`). The IS never touches the database directly.

### 3.3 Session-Scoped Memory

Sessions have context that persists within a session window (4h personal, 30min others) with automatic compaction:

```
Conversation messages accumulate
    ↓
When HISTORY_TOKEN_BUDGET (12,000) approached:
    ↓
Compaction runs → 5 structured memory blocks
    ↓
identity | user_model | continuity | goals | entity_context
    ↓
Next session bootstraps from these blocks (<100ms)
```

The user experiences continuous relationship. The infrastructure stays clean and never degrades.

### 3.4 Hub Protocol as IS↔Backend Contract

```
IS Agent Tool Call
    ↓
POST /api/hub/entities         (create/search)
GET  /api/hub/entities/:id     (read)
POST /api/hub/events           (write via event chain)
POST /api/hub/memory           (store knowledge fact)
GET  /api/hub/memory/search    (semantic search)
POST /api/hub/proposals/:id/actions  (governance)
```

Bearer auth with `pod.agentApiKey`. Each AI surface has its own dedicated API key. **Never change a surface's API key without explicit instruction.**

## 4. Frontend: Three UI Systems

This is the most important architectural fact for any UI work in 2026.

### 4.1 System 1: HeroUI — Apps (PRIMARY for new work)

Used in: `apps/studio`, `apps/crm`, `apps/hub`, and all new feature packages.

```
@heroui/react       (components: Card, Button, Input, Tabs, Table, etc.)
Tailwind CSS        (utility classes for layout and spacing)
@synap-core/heroui-preset  (Synap color palette as HeroUI theme)
```

**Rules:**
- Use `text-foreground/N` opacity tiers for text hierarchy on translucent panes.
- Use `bg-default-*`, `border-divider`, `text-foreground-*` HeroUI semantic tokens.
- Card/Button/Input/Tabs: always use `@heroui/react` primitives (not custom implementations).
- Never use `text-default-X` on translucent panes — use `text-foreground/N`.
- For all new views, adapters, and app-level UI: use HeroUI.

### 4.2 System 2: Tamagui — Legacy (DEPRECATED, do not add new usage)

Used in: existing `packages/views/` implementations (list, grid, table), core view adapters (TableAdapter, ListAdapter, GridAdapter, KanbanAdapter), some older feature packages.

```
tamagui             (YStack, XStack, SizableText, Button, etc.)
@synap-core/ui-system  (Synap Tamagui components)
$primary, $background, $borderColor  (Tamagui theme tokens)
```

**Status**: Do not add new Tamagui usage. Existing Tamagui views remain functional but are not the target for new development. HeroUI replacements are registered under `heroui-*` keys in the ViewAdapterRegistry.

### 4.3 System 3: Plain CSS + Token Override — Browser V2 Shell

Used in: `browser/electron/renderer/src/` — the Electron desktop shell.

```
browser-theme.ts    (warm dark palette: bgBase '#15110D', accent '#C28A4A')
@synap-core/ui-system  (getCSSVariables, browserTokens, SYNAP_PRESET)
CSS variables       (--companion-*, --browser-*)
```

This is NOT pure plain CSS. It extends the Tamagui-based `@synap-core/ui-system` token system with CSS variable overrides for the warm dark palette. The Browser V2 shell (`CompanionLayout`, `ActivityBar`, chat surfaces) uses CSS `--companion-*` variables and HeroUI for specific feature panels (marketplace, settings).

**Key tokens:**
- Background base: `#15110D` (warm dark)
- Accent: `#C28A4A` (amber/gold)
- All UI components: concentric radius rule (parent_radius = child_radius + gap)
- No shadows anywhere — subtle borders for depth

## 5. Rendering Stack

### 5.1 Cell Runtime (`@synap-core/cell-runtime`)

The universal rendering unit. Everything visual is a cell:

```
cellRegistry.register({ kind: "my-cell", component: MyCell })
    ↓
<CellRenderer kind="my-cell" params={...} />
    ↓
Renders in the appropriate host:
  BentoCellHost   (12-col react-grid-layout dashboard widget)
  PanelCellHost   (right-docked side panel, tabbed)
  PageCellHost    (full-screen)
  EmbedCellHost   (inline in document or whiteboard node)
```

70+ built-in cells across 14 packages. Two AI capabilities:
- **Compose**: AI picks from built-ins, configures params, arranges on bento grids.
- **Create**: AI writes new cell types (HTML/JS), sandboxed in iframes, proposal-gated.

### 5.2 View Adapter Registry (`viewAdapterRegistry`)

The registry that bridges entity data to view UI. Registered adapters as of May 2026:

| Key | Framework | Status |
|-----|-----------|--------|
| `tamagui-list` | Tamagui | Legacy |
| `tamagui-grid` | Tamagui | Legacy |
| `tamagui-table` | Tamagui | Legacy |
| `tamagui-kanban` | Tamagui | Legacy |
| `tamagui-bento` | Tamagui | Active (bento is framework-agnostic) |
| `tamagui-graph` | Tamagui | Active |
| `tamagui-calendar` | Tamagui | Active |
| `heroui-kanban` | HeroUI | **New — use this** |
| `heroui-list` | HeroUI | **New — use this** |
| `heroui-table` | HeroUI | **New — use this** |
| `heroui-grid` | HeroUI | **New — use this** |

**Usage pattern:**
```tsx
const adapter = viewAdapterRegistry.resolve("heroui-kanban");
// → ViewAdapterDescriptor { key, label, framework, component }

// Or use directly via ViewRenderer with adapterKey:
<ViewRenderer adapterKey="heroui-kanban" entities={entities} config={viewConfig} />
```

`ViewAdapterProps` contract:
```ts
interface ViewAdapterProps {
  entities: Entity[];
  config: ViewConfig;       // { category, query, render? }
  viewId?: string;
  workspaceId?: string | null;
  onEntityClick?: (id: string) => void;
}
```

### 5.3 StructuredViewRenderer

The full-featured renderer used in Studio, CRM, and Browser apps. It accepts all the rich adapter props (query, render, onConfigChange, etc.) and dispatches to the named adapter. For most in-app use, prefer `StructuredViewRenderer` over raw `viewAdapterRegistry.resolve()`.

### 5.4 Surface Runtime (`@synap-core/surface-runtime`)

"Open anything anywhere" system:

```
SurfacePlacement:   main | side | floating | modal | popover | embed
SurfaceKind:        cell | entity | document | view | channel | url | app | artifact
SurfaceDisplayMode: compact | medium | full
```

A surface request (e.g. "open this entity in the side panel in full mode") resolves through `SurfacePlacement` to the appropriate host component. This is how entity-detail panels, bento widgets, and embedded views all share one navigation contract.

## 6. Data Flows

### 6.1 Entity Creation (Happy Path)

```
User types in capture bar (Browser)
    ↓
useCreateEntity() hook (synap-hooks)
    ↓
trpc.entities.create.mutate() (synap-client)
    ↓
POST /trpc/entities.create (Backend tRPC)
    ↓
ProfileResolutionService.resolveProfile(profileSlug)
    ↓
EventLog.insert({ type: "entity:created", payload, userId })
    ↓
pg-boss picks up event → entity-event-worker
    ↓
EntityService.materialize(event) → entities table
    ↓
Socket.IO emit "entity:created" → client cache invalidation
    ↓
TanStack Query refetches → UI updates
```

### 6.2 AI Write Operation (Agent Mutation)

```
User sends message to AI channel
    ↓
POST /api/hub/channels/:id/messages (Hub Protocol)
    ↓
IS receives message → OrchestratorAgent.processMessage()
    ↓
Agent calls tool (e.g. create_entity)
    ↓
Tool → POST /api/hub/entities (Hub Protocol)
    ↓
Backend: checkPermissionOrPropose()
    ↓
  if auto-approved: write → event chain → materialized
  if proposal: Proposal record → UI notification → user reviews
    ↓
Agent receives result (entity ID or proposal ID)
    ↓
Agent embeds reference in reply: [[entity:ID|Name]]
    ↓
Frontend renders inline chip → click opens entity panel
```

### 6.3 View Render Flow

```
WorkspaceView loads
    ↓
useViewData(viewId) → trpc.views.execute({ id: viewId })
    ↓
Backend: resolve scope profiles → compute columns → execute query
    ↓
Returns: { entities[], columns[], renderConfig }
    ↓
<StructuredViewRenderer viewType="kanban" entities={...} render={...} />
    ↓
Routes to KanbanAdapter (Tamagui) or HeroUIKanbanAdapter
    ↓
Renders grouped by render.groupByField (default: "properties.status")
    ↓
onEntityClick → SurfaceRuntime.open({ kind: "entity", id, placement: "side" })
```

## 8. What to Use When (Decision Guide)

| Task | Use |
|------|-----|
| New view type for apps/Studio/CRM | `heroui-*` adapter in `viewAdapterRegistry` |
| New view type for Browser V2 | `heroui-*` adapter (same registry, rendered via `StructuredViewRenderer`) |
| New UI component for app | `@heroui/react` + Tailwind CSS classes |
| New UI for Browser shell chrome | Plain CSS + CSS variable tokens from `browser-theme.ts` |
| New AI action | Hub Protocol tool → `checkPermissionOrPropose()` → event chain |
| New entity mutation | `useCreateEntity/useUpdateEntity` hooks → tRPC → event chain |
| New async background job | pg-boss worker in `synap-backend/packages/jobs/` |
| Dashboard widget | Cell type registration in `@synap-core/cell-runtime` |
| Agent writes data | Never bypass proposals. Always via `checkPermissionOrPropose()`. |
| New workspace template | JSON config file — entity profiles + view configs + automations. No code. |

## 9. Known Gotchas

- **`lucide-react` shadows globals**: `import { Map } from 'lucide-react'` shadows `new Map()` — alias conflicting names.
- **Hub Protocol ≠ tRPC**: `/api/hub/*` is Hono REST, NOT `/trpc/hubProtocol.*`.
- **Entity creation uses `profileSlug`**, not `type` (deprecated).
- **`documents.entityId` REMOVED** — reverse: `entities WHERE documentId = ?`.
- **Drizzle JSONB `.set()`**: use `drizzleSql` from `drizzle-orm`, NOT `sql` from `@synap/database`.
- **tRPC URL on pod**: `${podUrl}/trpc` (no `/api` prefix).
- **Hono**: static routes BEFORE `/:id`.
- **Drizzle enum**: TypeScript enum value, not string literal.
- **Some packages use `type-check`**, others `typecheck` — check `package.json` scripts.
- **Hub Protocol relation fields**: `type`, `sourceEntityId`, `targetEntityId` (not `fromEntityId`/`toEntityId`/`relationDefSlug`).
- **POST /api/hub/memory**: `embedding` field is optional (zero-vector fallback).
- **Hub Protocol entity search**: `GET /api/hub/entities?profileSlug=X&workspaceId=Y` (not `/entities/search`).
- **Entity creation via Hub Protocol always creates a proposal** — entity is NOT in DB until user approves.
- **`framer-motion`** is available in HeroUI apps — used in `kanban-ui` and `HeroUIGridAdapter`.

## 10. ADR Index (Key Decisions)

| ADR | Decision | Rationale |
|-----|----------|-----------|
| **UI-001** | HeroUI is the primary UI framework for all Synap apps | Tamagui is too web-only and adds build complexity; HeroUI + Tailwind is lighter, more composable, and used in all new apps |
| **UI-002** | Tamagui stays in `view-renderer` Tamagui adapters until replaced by HeroUI counterparts | Incremental migration; both coexist in the registry under different keys |
| **UI-003** | Browser V2 shell uses CSS variable tokens, not raw Tamagui or raw HeroUI | Shell chrome needs a distinct warm dark palette independent of app-level theming |
| **RENDER-001** | `ViewAdapterRegistry` + `CellRenderer` are the universal rendering contracts | All views go through the registry; all cells go through the cell runtime. No ad-hoc rendering. |
| **RENDER-002** | HeroUI adapters registered under `heroui-*` keys alongside Tamagui `tamagui-*` | Allows gradual migration without breaking existing views |
| **IS-001** | OrchestratorAgent + PersonaAgent are the two canonical agent types | Adding new agent types requires adding tools, not new agent classes; `agentType` is a free string |
| **IS-002** | All IS↔Backend communication via Hub Protocol REST | Never direct DB access from IS; Hub Protocol is the contract |
| **DATA-001** | Event chain is the primary mutation path | All writes go through the event log; CRUD endpoints are thin wrappers |
| **DATA-002** | AI writes always go through `checkPermissionOrPropose()` | Architectural safety gate; never bypassed; every write is traceable |
