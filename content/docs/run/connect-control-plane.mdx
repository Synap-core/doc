A pod is a complete, independent server. It owns its users, memberships, workspaces, projects and sessions, and it
trusts no outside service by default. Connecting it to the Synap Control Plane (or to another account service) is
optional, and does not put that service's user or pod identifiers into the pod's identity model.

## Sign in with a Synap account

By default, people sign in to a self-hosted pod with email and password. To also offer "Continue with Synap Cloud":

```bash
cd /opt/synap/deploy
sudo synap federation connect-cloud      # uses CONTROL_PLANE_URL, else https://api.synap.live
sudo synap federation status
sudo synap federation disable            # back to password sign-in only
```

`connect-cloud` accepts `--control-plane <url>` for another Control Plane and `--label <text>` for the button's label.
It sets `CONTROL_PLANE_URL`, regenerates the sign-in configuration and restarts Kratos. The first time someone uses the
button, they sign in once with their pod password to link the two accounts; after that, the button signs them in
directly.

## Register the pod with the Control Plane

A pod can be registered with the Control Plane at install time, with a single-use registration code (`spr_…`)
created for you by the Control Plane:

```bash
curl -fsSL https://github.com/synap-core/backend/releases/download/channel-stable/install.sh \
  | sudo bash -s -- --name <name> --register-token spr_… [--domain pod.example.com]
```

- `--name` is required with a registration code: it is the name the code was created for. Without `--domain`, the pod
  is served at `pod.<name>.synap.live`.
- Once the pod is healthy, it registers: the person the code was created for becomes its owner. A registered pod
  cannot also be given a pre-seeded admin (`--admin-password`); the two are exclusive.
- `--control-plane <url>` selects another Control Plane (default `https://api.synap.live`).

`sudo synap policy show` prints what the Control Plane may ask this pod to do, and
`sudo synap policy set-mode managed|self-hosted` changes it.

## What each side owns

| Side | Owns |
|---|---|
| The account service (for example the Synap Control Plane) | Its accounts, passwords, sessions and invitations, and its record of which people relate to which pods |
| The pod | Which issuers it trusts, its local identities, memberships and access decisions, workspaces, projects and its own sessions |
| The browser or app | Talks to both directly; carries only short-lived assertions or one-time receipts between them |

The account service never receives a pod session token.

## The federation endpoints

For people building an account service or debugging one. All are under `/api/federation` on the pod:

| Endpoint | Purpose |
|---|---|
| `POST /bootstrap` | Creates the first local owner of a fresh pod from a short-lived signed assertion, authorized by the pod's local installation secret. A second owner cannot be bootstrapped this way. |
| `POST /identity-links` | A signed-in person links their pod account to an account service. Returns a one-time receipt. |
| `POST /identity-links/consume` | The account service redeems the receipt, server to server. |
| `POST /access-grants` | Applies an accepted invitation: a signed assertion naming one workspace or project on the pod. |

Assertions are ES256-signed by the issuer, addressed to the pod's exact public origin, short-lived and single-use.
The issuer publishes its keys as a JWKS over HTTPS. The pod rejects issuers and key locations that resolve to private
or local network addresses.

The older provisioning endpoints `/api/provision/connect`, `/authorize-issuer`, `/seed-trust`, `/seed-admin` and
`/activate-member` are retired and answer with a retirement response.
