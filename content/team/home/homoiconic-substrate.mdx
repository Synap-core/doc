## The One Sentence — and its extension

The strategic North Star states the thesis in one line:

> **Every application is a configuration. AI writes the config.**
> *(see [North Star](/team/home/north-star))*

This paper makes that sentence rigorous, grounds it in the code that already exists, and then **extends it by one step** — the step that we believe is the actual breakthrough:

> **Every application is a configuration. So is every agent. The system, and the intelligence that authors it, are values in one language — and the boundary between thinking and doing is a single, inspectable membrane.**

The first sentence is shared by every low-code platform's marketing. The extension is not. The claim of this paper is that Synap has — largely by accident, through the disciplined pursuit of "emergent complexity from a few orthogonal primitives" — built the substrate in which *data, structure, UI, behavior, and the agents themselves* are all describable as one typed value, and in which an AI's stochastic output is quarantined behind a deterministic, reversible gate before it can touch reality. That combination is what makes reliable, recursive, AI-authored software possible.

## 1. The thesis: software as a value in its own language

The deepest idea in computer science that Synap is (re)discovering is **homoiconicity** — a system in which programs are represented using the system's own primary data structure, so that code and data are the same kind of thing (McCarthy's Lisp, 1960; the term itself from Mooers & Deutsch's TRAC). In a homoiconic system, a program can read, generate, and transform other programs as ordinary data, because there is no representational gap between "the thing" and "the description of the thing."

Synap is a homoiconic system whose primary data structure is **typed JSON over an entity graph**:

- An **entity** is `{ profileId, properties }` — a typed object. **[VERIFIED]**
- A **profile** is its type: a named schema with inheritance, defaults, and rendering hints. **[VERIFIED]**
- A **view** is a declarative expression over a collection of entities — *which* entities (scope + query) and *how* to show them (config). **[VERIFIED]**
- A **workspace** — a working application, with schema, views, layout, and a home dashboard — is instantiated from **one JSON document**. **[VERIFIED for the structural layer; [PARTIAL] for the behavioral layer — see §3.1 and §6]**
- An **agent** is *also* an entity (a row in the same `users` table as humans), and its actions are *also* values (proposals) in the same language. **[VERIFIED]**

The consequence: the same AI that writes a workspace definition can write the agent that maintains it, can write the view that visualizes it, and can write the next agent — because all of these are the same kind of value. Code that writes code, data that is also program. That is the homoiconic loop, and it is the precondition for everything that follows.

This is not a metaphor we are reaching for. It is the literal shape of the data model, and it is why "AI writes the config" is achievable here and is a science-fiction pitch elsewhere: elsewhere, "the app" and "the agent that builds the app" are different substrates with different representations; here they are one.

## 2. The complexity argument: layers are the runtime, not the system

The standard objection to "everything from one JSON" is that real software is irreducibly complex, and you cannot wish away that complexity with a config file.

The answer is in *Out of the Tar Pit* (Moseley & Marks, 2006), the canonical paper on software complexity. It distinguishes **essential** complexity (inherent in the problem) from **accidental** complexity (introduced by our solutions), and argues that the largest source of accidental complexity is **mutable state and control flow** scattered through a codebase. Its prescription: push as much of the system as possible into **declarative data**, and confine state-mutation and effects to a small, well-defined kernel.

Synap's architecture is, in effect, an industrial implementation of that prescription:

- The **three-layer data pattern** (`hooks → stores → client → backend → DB`), the package boundaries, the registries, the optimistic-mutation discipline — these exist so that **humans can maintain a large TypeScript codebase**. They are *machinery*, not *meaning*.
- The **declarative substrate** (profiles, property defs, views, workspace definitions, proposals, automations-as-flow-graphs) is where the *meaning* lives.

The reframe that organizes this entire paper:

> **The layered stack is the runtime. The typed JSON is the surface language. The compiler between them is the set of repositories, resolvers, and workers that turn a definition into live rows and live UI.**

Neither the AI nor a power user should ever have to know that `hooks → stores → client` exists. They express intent as a value in the language; the runtime executes it. Once you see the layers as a compilation target rather than the system itself, "generate the app from JSON" stops being audacious and becomes simply *"target the surface language instead of hand-writing the runtime."*

## 3. The four pillars, as they exist in the code

The substrate rests on four subsystems. Each was independently verified against the live backend. Each maps to a well-understood model from the literature, and each has real, named consolidation debt.

### 3.1 The Data Kernel — the homoiconic core **[VERIFIED, with one [PARTIAL]]**

The kernel is the entity graph and its type system.

**Entities are typed objects.** The `entities` table stores `{ profileId, properties: jsonb }`; the file header describes an entity as *"a projection (materialized view) of the event stream"* — i.e., the durable truth is the event log, and the entity row is a cache of replaying it. The `properties` blob is the source of truth for an entity's data and is validated against its profile's schema.

**Profiles are types.** The `profiles` table names a `slug` (the type name), supports single inheritance via `parentProfileId` (a webinar profile extends an event profile), carries `defaultValues` applied at creation, and declares how instances render (`defaultListRenderer` / `defaultDetailRenderer`, stored as a `RendererRef` discriminated union). `ProfileResolutionService` resolves profiles slug-first, walks the hierarchy, and computes effective scope.

**Property defs are typed fields with three-layer scoping.** A field's value type is drawn from a closed enum (`STRING, NUMBER, BOOLEAN, DATE, ENTITY_ID, ARRAY, OBJECT, SECRET`); presentation richness (email, richtext, status, priority) lives in UI hints. The defining subtlety — and a genuine piece of type-theory in production — is the **three scope layers** keyed by `(profileId × workspaceId)`: *global* (`NULL/NULL`), *profile base* (`SET/NULL`), and *workspace overlay* (`SET/SET`). A single resolution rule, `getEffectiveProperties(profileId, workspaceId)`, walks the profile hierarchy root-to-leaf so children override parents, then applies the workspace overlay. The three-state `workspaceId` convention (`undefined` = unfiltered, `null` = base only, `string` = that workspace) is the discipline that keeps one workspace's fields from leaking into another.

**The graph has two edge mechanisms** — an important, easily-missed fact. *Semantic relations* (the `relations` table) are schema-free, bidirectional, emergent edges between entities (or even between cells — endpoints are polymorphic). *Structural links* are `entity_id`-typed properties: schema-defined, form-driven, one-directional. The two are bridged — a property def with a `relationDefId` auto-creates and auto-deletes a relation row as the property is written or cleared. This dual mechanism is exactly the "structured schema + emergent graph" duality the product philosophy promises.

**Views are declarative expressions.** A view stores `scopeProfileIds` (*which entity types*), a `query` blob (*which entities*: filters, sorts, search, grouping), and a `config` blob (*how*: column visibility, order, grouping). A structured view without a profile scope is a contradiction and is rejected at creation. View *type* (kanban, calendar, table, graph, bento…) is an open string; category (`structured | canvas | composite`) is *computed*, not hand-stored.

**A workspace is instantiated from one JSON document.** This is the headline, and it is real. `createWorkspaceFromDefinition()` is a production-wired, **idempotent, resumable 11-step pipeline** that takes a single definition and creates: the workspace, membership, profiles (reuse-or-create with scope/grant logic), property defs (correctly placed as base vs overlay), relation defs, display templates, structured views, auto-generated per-profile bento layouts, a home dashboard, seed entities (with `ref:profile:Title` → UUID resolution), flow views, and seed relations. It validates the entire definition against a Zod schema with cross-reference checking *before* touching the database, and on failure it records `failedStep` and preserves the workspace for retry rather than deleting it. The shipped `builder-workspace.json` (1,397 lines, 16 profiles, 6 views) is a working example: profiles inline their property defs, `valueType: "entity_id"` + `targetProfileSlug` declares a structural link *in the JSON*, and views are pure declarations (`{ type: "kanban", scopeProfileSlug: "task", groupBy: "task-status" }`).

> **The honest [PARTIAL]:** the definition JSON covers **schema + views + layout + dashboards + seed data + links** — the *structural* layer. It does **not** yet cover the *behavioral* layer: there is no `automations`, `channels`, or `commands` key in the definition interface or in any shipped template. Automations exist as a rich system of their own (a `flowDefinition` of nodes + edges with 12 node types, including `sub_automation` and `loop`), but they are created through a separate path, not the workspace definition. So *"one JSON → working app"* is true for the skeleton and the surfaces; it is **not yet true for the living behavior**. Closing this is the first item on the roadmap (§6).

**Mapping to the literature:** the entity/profile model is the entity-attribute-value design that Datomic (Hickey) makes temporal; the unification of types and values as one validated structure is the central idea of CUE (van Lohuizen); the "configuration as a total, analyzable value" stance is Dhall (Gonzalez); views over a typed relation are Codd's relational algebra (1970) in declarative JSON.

### 3.2 The Governance Membrane — where thinking becomes doing **[VERIFIED, with deliberate exceptions]**

This is the pillar that makes the rest *safe*, and it is the one competitors lack.

An AI agent is stochastic. The data kernel is total and analyzable. Between them sits a single function, `checkPermissionOrPropose()`, which is **the membrane**: an agent's intent cannot reach the database without passing through it. It returns a three-way discriminated union:

```ts
type PermissionResult =
  | { granted: true }                                   // execute directly
  | { granted: false; proposalId; summary; reviewUrl }  // quarantine as a proposal
  | { denied: true; reason }                             // hard stop
```

The decision is deterministic, computed from a precedence ladder: no-workspace (personal) → filesystem blocklist → RBAC → issuer trust → the agent path (capability allowlist → always-propose `ADMIN_ACTIONS` → `writesRequireProposal` → destructive-in-agent-owned-mode → per-channel capability grant → auto-approve whitelist → propose by default). Crucially, **trust is established at the auth boundary, never read from the request body** — the request's claimed `source` is audit-only provenance and must not gate authorization.

When the answer is "propose," the intended mutation is stored **as a replayable data envelope** in the `proposals` table — the table's own header calls it the structure that *"pauses an event until it is validated."* A composite (graph) proposal stores `{ operations: [...] }` — N entity-creates and M relation-creates as one reviewable unit. **The proposal is the program-as-value.** On approval, the stored envelope is *replayed* through the same canonical routers a human would hit, under a policy-gated approver.

Underneath runs an **append-only event spine** (a TimescaleDB hypertable; events are *"never updated or deleted, only appended"*). Every proposal is bound by `correlationId` and `requestedEventId` to its originating `.requested` event; approval appends `.validated`; a materializer worker performs the write and appends `.completed`. The lifecycle — **requested → (paused) → validated → completed** — is fully reconstructable, and only `.completed` events replicate across pods (replicating un-approved intent would leak it).

The boundary between the Intelligence Service and the backend is the cleanest expression of the whole design: the IS has **no database handle**. It speaks `/api/hub/*` REST, which dispatches into the *same routers and the same `checkPermissionOrPropose()` gate* a human hits. The agent never executes; it proposes, and the backend executes under the gate.

> **Honest exceptions (these qualify the romance and must be said):**
> - **[PARTIAL] Auto-approve is the widest opening in the membrane.** The default whitelist auto-approves routine creates/updates (`entity.create`, `view.create`, `document.create`, …) for trusted agents — they execute immediately with an after-the-fact audit row. The membrane is *strict* for destructive / admin / untrusted-issuer / `writesRequireProposal` paths and *permissive* for routine writes by default. "AI output is never a direct DB write" is therefore aspirational; the precise truth is "AI output that is dangerous is never an un-reviewed write."
> - **[RESOLVED 2026-06-07] The forked governance policy** in `@synap/jobs` has been extracted into a shared `@synap/governance-policy` package (pure, zero-dep) imported by both gates; the fork is deleted and a silent `"place"` drift was fixed. Verified by 27 new + 40 existing tests. See [Governance Hardening Plan](/team/platform/governance-hardening-plan) Wave A.
> - **[PARTIAL] Audit and spine writes are best-effort** (`.catch(() => {})`), so "every proposal is traceable to a `.requested` event" is a strong tendency, not a transactional invariant.
> - Reversibility is real but **per-subject-type** (document versioning, entity soft-delete); there is no single generic "undo this proposal."

**Mapping to the literature:** this is **event sourcing / CQRS** (Young; Fowler, 2005) over an **immutable log** (Helland, *Immutability Changes Everything*, 2015), with an authorization model that is essentially **object-capability security** (Miller, *Robust Composition*, 2006) — authority is a held, attenuable grant (the per-channel `canDraft/canPropose/canAct` flags can only *restrict*, never widen). The membrane is what lets a non-deterministic actor participate in a system whose core remains decidable.

### 3.3 The Actor Layer — agents as first-class nodes **[VERIFIED, with [PARTIAL] on durability]**

There is exactly **one** agent execution engine. "Different agents" are configuration differentials over a single `BaseAgent` template — the registry's own comment: *"Specialists are NOT separate classes. They are MainAgent instances with persona + disabledTools configured… one agent loop, many personalities/roles."* Every agent, regardless of role, has the same envelope: an `agentType`, a system prompt, a tool set (resolved from capability *categories*), a step budget, and optional model/temperature overrides. The CEO-agent and the coder-agent are the same socket with different things plugged in.

**Agents are first-class identities.** An agent is a row in the **same `users` table** as humans, distinguished by `userType: "agent"`. It carries `createdByUserId` (the human it belongs to), can be granted workspace membership and even **own a workspace** (`governanceMode: "agent-owned"`, where the agent holds creative authority but every irreversible action still requires a human-approved proposal), and authenticates via scoped API keys whose `linkedUserId` attributes its work to the human's timeline. A `parentAgentId` column exists for agent-of-agent lineage.

**The loop is ReAct.** The reason → act → observe cycle (Yao et al., *ReAct*, 2023) is not hand-written; it is the AI-SDK's multi-step tool-calling loop bounded by `maxSteps`, with `onStepFinish` as the observe hook, self-repair of malformed tool calls, and lazy tool discovery (the model activates extended tool groups mid-loop). The agent's "current activity" is projected into a state registry and streamed — the actor's observable status.

**Tools are the actor's message surface, and writes become proposals transparently.** Tools are Zod-schema-validated and grouped by intent. There is *no* `create_proposal` tool: a write tool calls the backend, the membrane decides execute-vs-propose, and the IS scans results for `{status: "proposed", proposalId}` and surfaces them. The agent does not *choose* to propose — proposing is enforced beneath it.

**Agents spawn and message agents.** `dispatch_agent` activates another agent (ephemeral in-process, or a parallel branch with its own channel + UI, or a deliberative A2A debate), propagating identity to the sub-agent, which runs its own `BaseAgent` loop and can itself dispatch. `query_agent` is the read side. This is the **actor model** (Hewitt, 1973; Agha, 1986): everything is an actor, actors spawn actors, they communicate by messages — and the philosophical frame is Minsky's *Society of Mind* (1986): intelligence as a society of simple, composed agents.

**Orthogonality is preserved.** `agentType` (a free string governing prompt + tools *within* an IS) is cleanly orthogonal to `intelligenceServiceId` (which IS instance handles a request). Resolution is capability-first → workspace default → user preference → failover → env. The rule "never add per-agent or per-channel IS routing" is honored in code.

> **Honest [PARTIAL]:** runtime spawning exists; **durable self-replication does not**. No path lets an agent create a new *persistent* agent — `parentAgentId` is written by no provisioning code, and `agent.create` is an `ADMIN_ACTION` (always human-gated by design). There are also **two agent-identity stores** (the `users` row vs. a separate `agents` catalog table) and an unfinished dual-write migration. The actor model is *live at execution time* and *consolidating at the persistence layer*.

### 3.4 The Transport — channels as message passing **[VERIFIED; 7 types, not 6]**

Communication between actors — human, AI, and external service — is message passing over typed **channels**. There are **seven** types (`thread, personal, sub_thread, feed, external, agent_collab, group`; the "6 types" in older docs predates the multiplayer `group` type). Messages carry full provenance (`authorType: human | ai_agent | external | bot`, routing attribution, an integrity hash chain).

**Agents are first-class channel members.** The `channel_members` table holds a `memberId` that may be a human or an agent (both live in `users`), a `memberKind`, and **per-member capability flags** (`canDraft / canPropose / canAct`) that feed directly into the governance membrane — the conservative default is *propose, not act*, and these flags can only tighten, never widen, RBAC. This is capability-based authority expressed at the conversation layer.

**Agent-to-agent collaboration is real.** In an `agent_collab` channel, an external agent posts (`postToA2AIChannel`, governed by a lightweight `a2ai.join` proposal for newcomers), and a pg-boss job triggers the resolved IS to respond *as another agent* in the same channel; `pollA2AIChannel` lets external agents read replies without holding a connection. Agent posts → agent reads → both are messages in one channel.

**The Hub Protocol is the single external boundary.** All IS/external-agent traffic goes through `/api/hub/*` (Hono REST, 43 resource sub-routers, scope-based bearer/session auth). The large tRPC `hubProtocolRouter` exists but is *not* mounted at the wire — it is reached only in-process via `createCaller` from the REST handlers. So "never tRPC" is true at the external boundary; internally, REST is the boundary and tRPC is the shared implementation.

> **Honest [PARTIAL]:** membership is not yet unified — `group` channels use the modern `channel_members` table while `agent_collab` still uses a legacy `metadata.participants` array; and the REST/tRPC dual surface keeps two hand-synced definitions per resource.

## 4. The unifying principle: one socket, one loop, one language

The four pillars are not four ideas. They are one idea seen from four sides.

**One socket, different content.** A cell, a view, an automation, and an agent are the same universal node differentiated only by configuration — exactly as every biological cell shares identical machinery and differentiates by what it expresses. This is the resolution of a tempting error: the power is *not* "the same agent stacked fractally" (self-similar recursion is emergent but *undirected* — it has no CEO). Nor is it pure layered abstraction (directed but *not* self-similar — a transistor is not a tiny CPU). It is **same structure, different content**: a uniform socket that gives composability and uniform tooling, populated by differentiated goals, tools, context, and altitude that give directed power. The CEO-agent and the coder-agent share an envelope; their *expression* differs.

**One loop, at every altitude.** The feedback cycle is universal, and in Synap it has a precise four-beat shape that unifies the pillars:

> **stochastic generation → total validation → governed execution → observation → (repeat)**
>
> the agent *thinks* (3.3) → its output is a *value in the total kernel language* (3.1) → it executes as a *governed, reversible proposal* (3.2) → the result is *observed* via events and channels (3.2, 3.4) → which feeds the next turn.

This is ReAct, generalized from "one agent reasoning over tool calls" to "the entire product as a feedback system." It is also the answer to the apparent contradiction between §3.1 (the kernel must be *total and analyzable* for governance to work) and §3.3 (an agent is *stochastic and may not terminate*): the non-determinism is **quarantined to the generation step**, and the artifact it emits is always a deterministic, typed, inspectable value. The membrane is the phase boundary between the stochastic and the total.

**One language, reflected.** Because agents are entities and their actions are values in the same language that describes data and UI, the system can describe *itself* in itself — the property Brian Cantwell Smith called **reflection** (*Procedural Reflection*, 1982). The interface that composes agents is rendered by the same cell system the agents use to build interfaces; the architecture documents itself as a queryable graph *inside Synap* (the Builder workspace's living graph — see [North Star](/team/home/north-star)). The snake eats its tail, productively. This reflective closure — not any single feature — is the moat.

## 5. The boundary of the dream (so we don't lie to ourselves)

"From one JSON, any app, any feature, automatically" is true **within a closure** and false outside it. Naming the boundary precisely is what separates this from the low-code graveyard.

**Composition is infinite; atoms are finite.** The JSON can compose and configure without limit — but only over a finite set of *atoms*: the cell primitives, the tool primitives, the kernel operations, the automation node types. The moment a feature needs a genuinely new atom — a novel rendering behavior, a new tool, logic no primitive expresses — code is required. Therefore:

> **The single metric that determines whether the vision is real is: how small and how complete is the atom set** — small enough to reason about, complete enough that the overwhelming majority of "any app" is pure composition, and only the rare new atom needs a human engineer.

And the escape hatch closes the loop: **a new atom is added through a proposal** — governed, reviewed, merged — the same membrane as everything else. The one path out of the JSON closure runs through the same gate as the paths within it.

**Total, not Turing-complete — on purpose.** The data/view/automation language must remain **analyzable**: SQL, Datalog, CUE, Dhall, and spreadsheet formulas are all deliberately *not* Turing-complete, precisely so their behavior can be reasoned about before execution. Synap's governance model *requires* this — you cannot show a reviewable, reversible proposal for a computation whose outcome is undecidable. **Governance-by-construction and decidability are the same constraint.** A total surface language is not a limitation we tolerate; it is the property that makes the membrane possible. (The stochastic agents are the one Turing-complete-ish element — and they are quarantined, by design, behind the total membrane.)

**The cautionary precedent.** Chris Granger's *Eve* attempted almost exactly this — one language unifying data, query, and UI for end-user and AI programming — and did not survive, primarily from over-ambition with no incremental adoption path. Synap's advantage is that it is *not* starting from a blank language: the substrate already exists as the config that flows through a shipping product, and the path is **consolidation, not invention**.

## 6. What exists vs. what must be built

The roadmap is not speculative — it is the set of consolidation gaps the four pillars revealed. Each item makes the substrate more uniform; none requires a new paradigm.

1. **Bring the behavioral layer into the definition JSON.** Today a workspace definition yields schema + views + layout + seed data, but **not** automations, channels, or commands (§3.1). The substrate is not whole until *behavior* is as declarable as *structure*. Add `automations`, `channels`, and `commands` to the `WorkspaceDefinition` schema and the `createWorkspaceFromDefinition` pipeline. **This is the highest-leverage single change**, because it is what turns "JSON → skeleton" into "JSON → living application."

2. **Define the universal node schema.** Today a "renderable unit" is split across `widget_definitions` (cell types), `cell_instances` (placed cells), and `views` — and the frontend `CAPABILITIES_MANIFEST` is hand-synced to the `widget_definitions` table by a startup seeder (§3.1). Write the *one* typed shape that a cell, a view, an automation, and an agent are all specializations of. That schema **is** the kernel; everything else is a projection of it. This is the most load-bearing artifact in the entire vision.

3. **Enumerate and bound the atom set.** Catalog the finite primitives that require code (cell primitives, tools, kernel operations, automation node types), publish their count, and formalize the single rule for adding a new one (→ a governed proposal). This converts "it can do anything" from a slogan into a measurable, defensible claim (§5).

4. **Unify agent identity and enable durable spawning.** Collapse the two identity stores (`users` row vs. `agents` catalog), finish the dual-write migration, and make `parentAgentId` real so an agent can — under the existing `ADMIN_ACTION` gate — create a *persistent* sub-agent (§3.3). Recursive organizations of agents require durable lineage, not just ephemeral in-process dispatch.

5. **Extract the shared governance policy.** Eliminate the forked `DEFAULT_AUTO_APPROVE` / `ADMIN_ACTIONS` mirror in `@synap/jobs` into a lower package both `api` and `jobs` import (§3.2). One source of truth for the membrane's policy.

6. **Unify channel membership.** Migrate `agent_collab`'s `metadata.participants` array onto `channel_members` so agent membership is uniform across all seven channel types (§3.4).

7. **Tighten the membrane where it matters, and make audit durable.** Make the auto-approve trade-off an explicit, per-workspace policy rather than a silent default, and make the proposal/event audit writes transactional with the mutation they describe rather than best-effort (§3.2).

8. **(Stretch) Reflect the substrate into its own authoring UI.** Render the agent-composition and automation surfaces *as cells over agent/automation entities* — so the tool that builds the system is built by the system (§4). This is the reflective closure; it is the proof that the substrate is complete.

A useful test for any future change: **does it let us delete something?** If unifying these layers does not let us remove a registry, a table, or a hand-sync, it is decoration, not consolidation. The whole force of this paper is that these were never separate systems.
