# Browser V2 Surface Session Bridge

**Status:** bridge implemented in Browser store, V1 behavior preserved.

This report explains what already existed, what was added, and how the next agent should build on it.

## What Already Existed

Browser already had most of the product behavior we want:

- main content tabs in `mainContentTabs`
- side panel tabs in `sidePanelTabs`
- active tab tracking per app in `activeMainContentTabIdByApp`
- side-panel dedupe through `cellResourceKey`
- drag/drop moves between side and main
- `openSurface(surface)` as a compatibility entry point
- deprecated wrappers like `openDocument`, `openView`, `openChannel`, `openSidePanelTab`

The issue was not missing behavior. The issue was that this behavior was Browser-specific and not visible as a canonical platform session.

Synap also already had the platform contracts:

- `@synap-core/surface-runtime` owns `SurfaceDescriptor`: what wants to open.
- `@synap-core/renderer-runtime` owns `RendererTarget`: how it should render.
- `@synap-core/cell-runtime`, `view-renderer`, and `profile-renderer` own content rendering.
- `@synap-core/workspace-state` owns flat URL/open state, useful for routes but too small for Browser V2 placement stacks and breadcrumb trails.

## What Was Added

`@synap-core/surface-session` is now mirrored inside Browser's `appStore`.

Browser state now includes:

- `surfaceSession: SurfaceSessionState`
- `getSurfaceContextSnapshot()`
- `syncSurfaceSessionFromLegacyState()`
- `useSurfaceSession()`

The existing Browser actions now dual-write into `surfaceSession`:

- `openSurface`
- `openSidePanelTab`
- `openViewTab`
- `openDocument`
- `openChannel`
- `openUrl`
- `openSidebarWebview`
- `openEntityInPanel`
- side-panel close/focus
- main-tab close/focus
- side-to-main and main-to-side movement

AI chat is intentionally mapped as a `companion` session placement while the old V1 UI can still render it through the legacy side-panel path. This gives Browser V2 the correct future semantics without breaking current behavior.

## Interaction With Existing State

For now, Browser's legacy state remains the behavior owner.

`mainContentTabs`, `sidePanelTabs`, `activeView`, `entityPanel`, and current wrappers still drive the V1 UI.

`surfaceSession` is the canonical mirror for:

- Browser V2 shell rendering
- companion context
- breadcrumb trails
- future Eve/web host alignment

This means the bridge is intentionally not a full replacement yet.

The next implementation step is to invert ownership only after parity is proven:

1. V1 actions continue to update legacy state.
2. Those same actions update `surfaceSession`.
3. Browser V2 reads from `surfaceSession`.
4. Once Browser V2 behaves correctly, wrappers become thin calls into `openSurfaceInstance`.
5. Legacy tab/panel state can then be reduced or derived.

## Infra Meaning

The front-end state model is now layered:

| Layer | Package / Store | Responsibility |
| --- | --- | --- |
| Open intent | `@synap-core/surface-runtime` | Entity/view/document/app/artifact descriptors. |
| Renderer choice | `@synap-core/renderer-runtime` | Cell/view/profile/iframe/external target resolution. |
| Live session | `@synap-core/surface-session` | Placement stacks, active focus, trails, AI-visible context. |
| Browser V1 host | `browser/appStore` legacy fields | Existing UI behavior and backwards compatibility. |
| Browser V2 host | `@synap-core/spatial-shell` + future adapter | Spatial shell rendering from `SurfaceSessionState`. |

The important constraint is: app packages should not learn Browser internals. They should request surfaces and attach metadata. Browser decides placement and renders the session.

## What The Browser Bridge Built Upon

The bridge uses existing Browser concepts instead of replacing them:

- side tab ids become surface instance ids for side surfaces
- main tab ids become surface instance ids for main surfaces
- existing dedupe remains active
- existing close/focus actions also close/focus the matching surface instance
- existing `resolveSurfaceRenderer(surface)` remains the renderer decision point
- `cellToSurface` adapts legacy cell calls into surface descriptors

This keeps old Browser behavior stable while giving Browser V2 a host-agnostic state model.

## Agent Instructions For Next Actions

Next agents should follow this order.

1. **Do not rewrite Browser tabs first.**
   Keep `mainContentTabs` and `sidePanelTabs` working until Browser V2 has parity.

2. **Render Browser V2 from `surfaceSession`.**
   Build a small adapter that maps:
   - `session.placements.main` to `BrowserV2Shell.mainTabs`
   - `session.placements.side` to `BrowserV2Shell.sideTabs`
   - `session.placements.companion` to `CompanionIsland`
   - `session.activeSurfaceId` to the top context island

3. **Wire breadcrumbs from trails.**
   Use the active surface's `trail`. Do not derive breadcrumbs from backend hierarchy.

4. **Feed AI from the snapshot.**
   Use `getSurfaceContextSnapshot()` or `buildSurfaceContextSnapshot(surfaceSession)`.
   Do not import CRM/Data/View state into AI chat.

5. **Add renderer bridges.**
   Implement one host renderer switch for `RendererTarget`:
   - `cell` -> `cell-runtime`
   - `view` -> `view-renderer`
   - profile/entity -> `profile-renderer`
   - `iframe-srcdoc` -> generated app iframe host
   - `external-app` / `url` -> Browser URL/webview path

6. **Improve metadata at call sites.**
   As CRM/Data/Views migrate, pass better titles, profile slugs, summaries, and selection metadata into surfaces.

7. **Only then consolidate old state.**
   Once Browser V2 runs from `surfaceSession`, make legacy wrappers call the session adapter first and derive legacy state only where V1 still needs it.

## Guardrails

- Do not persist full `surfaceSession` yet.
- Do not store secrets, full document contents, or hidden AI reasoning in `SurfaceContextMetadata`.
- Do not make the companion inspect DOM or app-specific stores.
- Do not merge `workspace-state` and `surface-session`; use `workspace-state` for route/URL sync and `surface-session` for live host placement.
- Do not make `cell-runtime` responsible for window/panel placement.
