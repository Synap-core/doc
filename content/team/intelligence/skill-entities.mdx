# Skill: Entity Management

You can create and update entities using `create_entity` and `update_entity`.
Entity mutations may require user approval depending on workspace governance settings.

## What is an entity?

An entity is a structured record — a task, contact, project, document reference, product, etc.
Each entity has:

- A `title` (required)
- A `profileSlug` linking it to a profile type (required)
- `properties` JSONB object containing field values
- Optional long-form `content`, stored as a linked versioned document
- Optional project filing, role facets, and provenance when they are known

## Schema-first creation

`create_entity({ title, content })` is only suitable for a simple note-like
record. Before creating a task, person, event, question, or custom kind, use
the live schema rather than guessing property names:

1. Use `orient` or `list_profiles` to identify the candidate kind.
2. Search or resolve identity when the request may refer to something that
   already exists. A title match alone is never a reason to merge records.
3. Use `discover` for the selected profile. It returns the live property model,
   including required fields and allowed values.
4. Submit every fact already known in one governed write: `properties`,
   `content`, existing `projectId`, and applicable facets.
5. Read the write receipt. A `proposed` result is waiting for review, not a
   created entity. Only propose a follow-up update when new information is
   actually available.

Do not silently select a workspace. A discovery without an explicit workspace
uses the base/pod schema. A workspace supplied explicitly may add only that
workspace's overlays.

## Kind vs. Facet — before you create

Not every mention of a role or relationship state means a new entity. Check `list_profiles` first: if the type is a `profileKind: 'role'` profile (e.g. `client`, `partner`, `prospect`, `sponsor`), the target already exists as some other entity (usually `person` or `company`) and the message is stating a new role for it — resolve identity first (search / strong-signal match on email, phone, url), then call `attach_facet` on the existing entity. Never `create_entity` a second time to express "this person is also a client." See [Kind + Facets](/docs/architecture/concepts/kind-and-facets) for the full model.

```yaml

attach_facet({
  entityId: "<existing-person-entity-id>",
  profileSlug: "client",
  status: "active",
  properties: { source: "referral" }
})

```

`attach_facet` is governed the same way entity creation is — a `status: "proposed"` result means it's awaiting user review, not an error. A facet cascades with its parent entity: detaching it never deletes the underlying person/company, and deleting the parent removes the facet with it.

## Creating an entity

```yaml

create_entity({
  profileSlug: "crm-contact",
  title: "Acme Corp - Follow up",
  properties: {
    email: "hello@acme.com",
    status: "lead",
    owner: "<user-id>"
  }
})

```

**Workflow:**

1. Call `orient` or `list_profiles` to find the right profile type.
2. Call `discover` for the selected profile before sending non-trivial properties.
3. If no suitable profile exists, create one with `create_profile`, then repeat discovery.
4. Pass `profileSlug` and only keys returned by the live schema.

## When to create a new profile vs use an existing one

- **Use existing**: The workspace already has a profile that matches (check `list_profiles`).
- **Extend a base type**: The user needs something that's conceptually a specialization of a system type. E.g. "webinar" extends "event", "lead" extends "person". Use `create_profile` with `parentProfileSlug`.
- **Create new root**: Only for genuinely new concepts that don't fit any base type.
- **Don't create a profile** when a generic type works fine. A quick note → just use `note`. A task → use `task`. Don't over-specialize early.

## Proactive entity creation

When the user mentions trackable items in conversation, capture them proactively:

- Use one complete write when all known fields concern one entity.
- Use a composite graph proposal for several entities, roles, or explicit
  relationships that should be reviewed together.
- State the actual receipt outcome: created, reused, proposed, or partial.

## Updating an entity

```yaml

update_entity({
  entityId: "<entity-id>",
  properties: {
    status: "customer",
    notes: "Signed contract 2026-03-01"
  }
})

```

`update_entity` merges properties — you only need to pass the fields that changed.

## Searching for entities

Use `search_entities` or `search_unified` to find entities before creating duplicates.
Always search first when the user refers to an existing entity by name.

## Property value conventions

- `select` / `multi_select`: pass the option `value` (not the label). E.g. `"status": "in_progress"`.
- `date`: ISO 8601 date string `"2026-03-15"`.
- `datetime`: ISO 8601 datetime `"2026-03-15T10:00:00Z"`.
- `boolean`: `true` / `false`.
- `number`: numeric value (no quotes).
- `user`: workspace member user ID (UUID).
- `relation`: target entity ID (UUID).

## Linking entities to the conversation

After creating or finding key entities, call `link_entity_to_thread` to surface them in the thread sidebar.
This helps the user navigate to the entity directly from the chat.

## Rules

- Never create duplicate entities — search first.
- Never create a second entity to express a role or relationship state — attach a facet instead.
- Always use `profileSlug` (not the deprecated `type` field).
- Batch related entities into one composite proposal when creating multiple (e.g. a project + its tasks).
- For large bulk imports, use `create_branch` to process in a separate branch.
- Entity creation and update are subject to workspace governance (may create proposals).
