## The reframing finding (new, important)

**A structural materialization bug exists, independent of the original C3 framing.** The materialization hook (`setup-event-broadcasting.ts:49-122`) is registered on the **singleton** `eventRepository`, but `.validated` events are appended through a **fresh `new EventRepository(sql)`** (in `auditLog`, routers, materializer) whose per-instance `eventHooks` array is empty. So a `.validated` append fires **no hook** → no `materialize` job. Proposal types that rely on the hook→materializer path (**view / profile / command**, and generic relation/whiteboard/workspace) flip to **APPROVED but never materialize**.

- **Why it's not on fire:** high-traffic types (entity create/update, document, channel, composite graph) are materialized **inline** in `proposals.ts approve`, bypassing the hook entirely → that's why 0 orphans in 238.
- **Status:** HIGH severity for the affected types, ~LOW real-world incidence today (those types are rarely proposed-then-approved here). **Confidence: high code-read, NEEDS one dogfood** (approve an AI-proposed *view*, check it's created).

| **B2-3** | Fix **C3 swallow** (defect a): flip→APPROVED only after `.validated` confirmed | Real bug, HIGH severity × LOW likelihood (needs the append to throw). Same code area as B2-2 (`proposals.ts` approve + batchApprove, unconditional status flip). | **Fix with B2-2.** |
| **B2-4** | `auditLog` **strict mode** scope | Only **2** governance-critical callers (`proposals.ts:1477` approve, `:1713` batchApprove — both `phase:"validated"`); all other ~6 callers are benign trail. | **Add `throwOnError` used only by those 2.** Leave shared helper swallow-by-default. |
| **B2-5** | **TX-1** (proposal INSERT + `.requested` append atomic) | Both are Drizzle on one pool → implementable, **S–M, low risk**. Plumb optional `tx` into `logEvent` + `createPendingProposal`; keep notifications outside the tx. | **B2-6** | **TX-3** (materialize write + `.completed` atomic) | **NOT feasible as one tx:** cross-abstraction (Drizzle repos vs raw-`sql` EventRepository), event emission buried in repo methods, and **non-rollbackable `storage.upload()` inside the create path** (pool starvation risk). | **Do NOT attempt the transaction.** Solve via idempotency + at-least-once (B2-7). |
| **B2-7** | **Idempotency** fixes (the real B2 write) | Materializer **B (sync)** already fully idempotent (ON CONFLICT). Materializer **A** gaps: `view.create` doc/storage side (fresh UUIDs on retry → orphan docs); **`command.execute` re-runs the shell on retry** (sharpest); `emitSideEffects`+worker `.completed` sit in the retry region (replay the write); double-`.completed` (repo + worker both emit). | **Do the A fixes**, priority on `command.execute` once-only + moving side-effects out of the retry region. **M, medium risk.** |

## Recommended sequence

1. **B2 correctness (highest urgency):** B2-2 (hook bug) + B2-3 (flip-after-validated) + B2-4 (strict auditLog) — one code area (`proposals.ts` + event-repo wiring). **Dogfood: approve an AI view → confirm it materializes.**
2. **B2-5 TX-1** — atomic proposal+`.requested` (also fixes correlation linkage).
3. **B2-7 idempotency** — `command.execute` once-only + side-effects out of retry region + `view.create` doc-side.
4. **B3 Phase 1** — provenance on entities/documents/relations (+ migration `0106`).
5. **Drop:** TX-3 (infeasible). **Defer:** B3 Phase 2/3. **Skip:** profiles.

Each step is verifiable (typecheck + unit) but the materialization/idempotency fixes **need runtime dogfood on CT101** to truly confirm — so they ship as runtime-verified waves, not typecheck-only.
