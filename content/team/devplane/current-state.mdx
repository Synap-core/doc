This document consolidates everything we've built in DevPlane, how it all fits together, and the story/feature organization for what comes next.

## What DevPlane Is Today

DevPlane is a **vertical Synap app** — a purpose-built UI lens over a Synap data pod. No separate database, no separate backend. Every entity is a typed Synap profile, every read/write goes through tRPC, every session is authenticated through the shared CP → pod handshake.

**Live:** [devplane.staging.synap.live](https://devplane.staging.synap.live)
**Code:** `synap-app/apps/devplane/`

## Architecture Overview

### The Three-Layer Rule

```
React Component
  → lib/devplane/hooks.ts        (useApps, useCreateDevplaneEntity…)
    → @synap-core/client         (tRPC + TanStack Query)
      → Next.js /trpc proxy
        → Synap backend pod :4000/trpc
          → Drizzle ORM → PostgreSQL
```

**Components never call tRPC directly.** They always go through a hook in `lib/devplane/hooks.ts`. This is the single most important convention — it keeps the data layer testable, mockable, and replaceable.

### Provider Tree — Two Tiers

**Tier 1 — `app/providers.tsx` (always active):**
```
NextThemesProvider
  HeroUIProvider
    SynapProvider              ← auth context, workspaceId
      AppStoresSync            ← Zustand hydration
        AppTRPCProvider        ← tRPC client with 401 interceptor
          RegistryBoot
            CellRuntimeWrapper
              CommandPaletteProvider
                {children}
```

**Tier 2 — `app/(app)/layout.tsx` (gated — only when workspace is ready):**
```
AuthGuard                      ← full-page overlay if unauthenticated
  WorkspaceReadinessGate       ← state machine: idle → checking → bootstrapping → ready
    AppSocketProvider          ← Socket.IO → pod (only after readiness)
      RealtimeBridge           ← cache invalidation via socket events
        AppShell + DevPlaneSidebar + {children}
```

**Why Socket.IO is gated:** tRPC goes through the Next.js `/trpc` proxy, but Socket.IO connects directly to the pod URL. Connecting before workspace readiness produces cross-origin WebSocket errors with no benefit.

### Startup State Machine

`hooks/useWorkspaceReadiness.ts` — runs before any app content renders:

```
idle
  → no workspace in localStorage  → no_workspace → redirect /onboarding
  → workspace found               → checking

checking  (fetching profiles.list)
  → all 19 profiles present       → ready ✓
  → profiles missing, first time  → bootstrapping

bootstrapping  (createFromDefinition with existing workspaceId)
  → done                          → rechecking

rechecking  (fetching profiles.list again)
  → all 19 profiles present       → ready ✓
  → still missing                 → waiting

waiting  (scheduled retry every 3.5s, max 4 silent)
  → profiles appear               → ready ✓
  → after 4 retries               → show "Check again" button
  → manual retry                  → reset bootstrappedRef → checking
```

Key files:
- `hooks/useWorkspaceReadiness.ts` — state machine, `REQUIRED_PROFILE_SLUGS` array
- `lib/builderWorkspaceDefinition.ts` — 19-profile `WorkspaceProposal` (source of truth)
- `hooks/useDevplaneSetup.ts` — first-login flow

### Auth Flow

1. User visits DevPlane → `AuthGuard` checks session
2. No session → full-page login overlay (not inline in app shell)
3. After login → `SynapProvider` holds `workspaceId` from localStorage
4. tRPC 401 errors → `clearSession()` + redirect to `/login`
5. Middleware protects `/onboarding`, `/stories`, `/api/*`, `/settings`, `/architecture`

Key files:
- `components/providers/AuthGuard.tsx` — full-page auth gate layout
- `components/providers/AuthRedirect.tsx` — redirect logic
- `components/providers/AppTRPCProvider.tsx` — tRPC client with 401 error link
- `middleware.ts` — route protection

## Package Ordering & Data Flow

### How Data Flows Through the System

```
User Action (UI)
  → Hook (lib/devplane/hooks.ts)
    → tRPC mutation/query (@synap-core/client)
      → Next.js /trpc proxy route
        → Synap backend (pod :4000)
          → Drizzle ORM → PostgreSQL
            → Socket.IO event (if subscribed)
              → RealtimeBridge invalidates TanStack Query cache
                → UI re-renders
```

### Key Wrappers

**`lib/devplane/hooks.ts`** — All data access goes through here:
- `useDevplaneEntities(profileSlug)` — generic list hook
- `useDevplaneEntity(id)` — single entity by ID
- `useCreateDevplaneEntity()`, `useUpdateDevplaneEntity()`, `useDeleteDevplaneEntity()` — CRUD mutations
- Profile-specific hooks: `useApps()`, `useFeatures()`, `usePackages()`, `useSnippets()`, `useDecisionRecords()`, `usePackagePublishes()`, `useIncidents()`, `useCrons()`, `useDeploymentTargets()`
- Channel hooks: `useEntityChannel()`, `useCreateFeatureWithChannel()`, `useSendChannelMessage()`
- Automation hooks: `useAutoCreateDeployment()`, `useAutoCreateIncident()`
- Workspace settings: `useMonorepoRoot()`, `useSetMonorepoRoot()`, `useLocalTerminalEnabled()`, `useToggleLocalTerminal()`, `useAiProviderSettings()`, `useUpdateAiProviderSettings()`, `useProviderConfigs()`, `useSaveProviderApiKey()`
- Deployment helpers: `useAppDeployments()`, `useAppDeploymentTargets()`

**`lib/devplane/intelligence/`** — Pure TypeScript utilities:
- `impact.ts` — `analyzeImpact()` — BFS traversal of package dependency graph
- `context.ts` — `buildFeatureContextMessage()` — builds markdown context for AI channel

**`lib/devplane/useRecipeRunner.ts`** — WebSocket recipe runner with per-step streaming

**`lib/devplane/vault.ts`** — Vault reference resolution (server-side only, never stores plaintext)

**`lib/devplane/seed.ts`** — `seedSynapStack()` — creates demo entities for the Synap stack

**`lib/devplane/snippetUtils.ts`** — Prompt snippet utilities

**`lib/devplane/config-schema.ts`** — Configuration schema validation

**`lib/devplane/recipeTemplates.ts`** — Recipe template definitions (kamal, shell, custom)

### Dependency Order

```
@synap-core/client     ← tRPC client, TanStack Query, types

@synap-core/ui-system  ← Shared UI components (if used)
```

## Story & Feature Organization

### Two-Level Hierarchy

**Features** are the main capabilities — the "what the system can do":
1. **Cell Renderer** — The rendering engine for all entity views (table cells, kanban cards, graph nodes)
2. **View Renderer** — The view system (table, kanban, calendar, graph, bento, timeline)
3. **AI Channel** — Persistent AI sessions per entity with context injection
4. **Agent Pipeline** — The state machine: idle → gathering_context → planning → executing → deploying → done
5. **Recipe Runner** — SSH command execution with live streaming
6. **Architecture Graph** — Living architecture map with React Flow + Mermaid
7. **Package Intelligence** — Health scoring, dependency graph, impact analysis
8. **External Access** — Webhooks, API access, automation subscriptions

**Stories** are user-facing scenarios — the "how a user experiences it":

### Proposed Stories

#### Architecture Graph
- "User can add any system component (frontend, backend, database, external API) and see it on the graph"
- "User can define workflows that connect components and see the flow visualized"
- "User can toggle between Graph, List, and Mermaid views of the architecture"
- "User can search and filter components by type, status, or tech stack"

#### AI Channel & Context
- "User can ask AI and it auto-pinpoints the context (entities/views opened)"

- "User can resume any work session — AI remembers the full history"

- "User creates a story and the agent automatically gathers context, plans, and executes"
- "User can approve/reject the agent's plan before execution"
- "User can see the agent's progress through each phase (gather → plan → execute → verify → deploy)"
- "User can retry a failed agent run with the same context"

#### External Access (Webhooks & API)
- "Any app can access any data pod data via the shared API + auth package"
- "An agent can call Synap and be directly connected to memory, event chain, and permission model"
- "Anyone can subscribe to Synap events and automate based on what's happening"

- "User can run impact analysis before publishing — see which apps need updating"

## Webhook & External Access Story

This is a major capability that deserves its own story cluster. The goal: **Synap as a platform, not just an app.**

### Three Access Patterns

**1. App → Pod Data (Read/Write)**
- Any app (DevPlane, CRM, Browser, custom) uses `@synap-core/client` to access pod data
- Shared auth package handles the CP → pod handshake
- tRPC routes are workspace-scoped — apps only see their workspace's data
- Code: `packages/core/client/` — tRPC client, query hooks, mutation helpers

**2. Agent → Synap (Memory + Events + Permissions)**
- Agents (OpenClaw, custom) connect via the agent identity system
- Agents get access to: memory (session compaction), event chain (pg-boss workers), permission model (proposals)
- Agents can create entities, read channels, propose changes
- Code: `synap-backend/` — agent routes, memory system, proposal engine

**3. External → Synap (Webhooks + Subscriptions)**
- External systems subscribe to Synap events via webhooks
- Events: entity created, entity updated, entity deleted, deployment succeeded, incident opened, package published
- Webhook payloads include entity data, event type, timestamp, workspace ID
- Users configure webhook endpoints in settings
- Code: `synap-backend/` — webhook system, event chain, subscription management

### Webhook Event Types

```
entity.created    → { profileSlug, entityId, workspaceId, timestamp, properties }
entity.updated    → { profileSlug, entityId, workspaceId, timestamp, changes }
entity.deleted    → { profileSlug, entityId, workspaceId, timestamp }
deployment.succeeded → { appId, version, commitSha, environment, timestamp }
incident.opened   → { incidentId, severity, affectedApps, timestamp }
package.published → { packageName, fromVersion, toVersion, bumpType, timestamp }
recipe.completed  → { recipeId, runId, success, duration, triggeredBy }
```

### Seeding Implementation

The seed function should live in `lib/devplane/seed.ts` and be callable from:
1. First-login flow (`useDevplaneSetup.ts`) — optional "seed with Synap stack" checkbox
2. Manual trigger from settings page
3. CLI command (`./tctl sync --seed`)

The seed function should:
1. Check if entities already exist (idempotent)
2. Create apps, packages, components, workflows
3. Create relations between them
4. Return summary of what was created
