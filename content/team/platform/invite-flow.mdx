## Overview

The invite flow allows a pod-admin operator to invite a new user to their self-hosted pod. The user accepts the invite, gets a Kratos identity created on the pod, and lands in the CRM (or any app) with the correct workspace automatically resolved — no manual pod URL entry required.

## Step Details

### Steps 1–2: Invite creation

The pod operator creates an invite from pod-admin. The backend stores an invite token and sends an email with a link to `https://{POD_ADMIN_URL}/invite/{token}`.

### Step 3–4: Accept invite form

`/invite/{token}` renders `AcceptForm`. The user enters their name and password. On submit:

```
POST /api/hub/setup/accept-invite
{ token, name, password }
```

The backend:
1. Validates the token (not expired, not already used)
2. Creates a Kratos identity for the user with the supplied password
3. Grants workspace membership

### Step 5: Redirect to CRM

After acceptance, pod-admin redirects to:

```
{NEXT_PUBLIC_CRM_URL}/login?podUrl={POD_URL}
```

No environment variable configuration is needed — the pod URL comes from the invite token record.

### Steps 6–7: CRM auto-starts self-hosted login

The CRM login page checks for a `?podUrl=` query param on mount. If present, it immediately calls `startSelfHostedLogin(podUrl)` and renders `ManualLoginScreen` with the pod URL pre-filled. The user only needs to enter their email and the password they chose in the accept form.

### Step 8: whoami fetch

After the Kratos session token is returned, `handleKratosAuthenticated` fetches `GET /kratos/sessions/whoami` before calling `finalizeSession`. This populates `userId`, `email`, and `name` from the start, which is required for the workspace setup cache key to be correct.

### Step 9: Session finalization

`finalizeSession` calls both:
- `storePodSession({ podUrl, sessionToken, userEmail })` — writes to `localStorage["synap:pods"]`
- `storeSharedSession(...)` — clears `synap-session` and `SYNAP_INSTANCE_URL` cookies first (prevents duplicates from any prior pod session), then writes the new active session

### Steps 10–11: Workspace resolution

`useWorkspaceSetup` (via `useCrmSetup`) runs the standard discovery sequence:

1. Search for a workspace with `settings.proposalId === "crm-personal-v1"`
2. Fall back to `legacyName: "CRM"` for pre-stamp workspaces
3. If a matching workspace is found → open CRM directly
4. If the user has other workspaces but none matched → `needs-picker` phase → workspace picker UI
5. If no workspaces at all → `createFromDefinition` → new CRM workspace

---

## Key Invariants

- The pod URL travels from the invite email → accept redirect → CRM `?podUrl=` param. No env var is needed on the CRM side.
- `userId` is always populated before workspace setup runs (whoami fetch in step 8).
- `storeSharedSession` always clears cookies before writing (step 9), so switching pods via an invite never leaves stale cookies from a previous pod.
- The `needs-picker` phase only fires if the user already has workspaces — first-time invited users with no workspaces get a fresh workspace auto-created.
