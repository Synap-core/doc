# Pod Federation Boundary

## Design rule

The Control Plane is an issuer and orchestration service, not part of the Data Pod's data model. The same protocol must work for any account service that a local Pod owner chooses to trust.

| Layer | Owns |
|---|---|
| **Issuer / Control Plane** | Account credentials, sessions, invitations, and its ledger of people related to Pods |
| **Browser or app** | Direct user interaction with each origin and the transport of short-lived assertions or opaque receipts |
| **Data Pod** | Trusted issuer approval, local identities, local sessions, workspaces, projects, and membership decisions |

The Pod never stores a Control Plane user ID or Control Plane Pod record. The Control Plane never receives a raw Pod session token.

## Normal sign-in

```text
User signs in to issuer
        |
        v
Issuer ledger chooses a reachable Pod and an optional requested scope
        |
        v
Issuer signs a short-lived user-exchange assertion for that Pod origin
        |
        v
Browser sends assertion directly to Pod /api/federation/exchange
        |
        v
Pod resolves (issuer, opaque subject) -> local user,
checks local access, then mints its own session
```

An issuer assertion is never a Pod session. The Pod must have both an approved issuer and a pre-existing generic identity link before it mints a session.

## Adding an existing Pod to an issuer account

This flow proves local access without handing the local session to the issuer.

```text
Browser (issuer session) -> issuer: create link intent
Issuer -> browser: short-lived identity-link assertion
Browser (direct Pod session) -> Pod: identity-links assertion
Pod -> browser: opaque one-time receipt
Browser -> issuer: intent + receipt only
Issuer -> Pod: receipt + issuer-signed receipt assertion
Pod -> issuer: Pod-authoritative access projection
Issuer -> issuer ledger: relationship and scopes
```

The issuer's ledger is a discovery and routing projection. It is not the authority for a Pod's local membership.

## Invitations and grants

The issuer can track an invitation and, after the recipient has an issuer account, issue a short-lived `access-grant` assertion for one exact workspace or project. The Pod checks the issuer's `membership:grant` capability, verifies the local target is active and not an administration workspace, then creates or updates its local membership idempotently.

Direct Pod invitations remain valid without an issuer session. They are a local Pod concern. A product may choose to offer an issuer-mediated invitation flow only when the inviting user is signed in to that issuer.

## Fresh managed Pod

A newly installed Pod has no local human owner and no trusted issuer. Its installer supplies a Pod-local bootstrap secret. The orchestrator signs a generic `initial-owner-bootstrap` assertion addressed to that Pod:

```text
orchestrator -> Pod /api/federation/bootstrap
  X-Pod-Bootstrap-Token: local installation secret
  body: { assertion }
```

The assertion contains a generic issuer subject, email, name, command ID, and Pod audience. It contains no external Pod ID, external account ID, external URL configuration, or raw session. The Pod creates its first local owner, records a generic issuer-subject link, and approves that issuer locally. A different human owner cannot subsequently be bootstrapped.

## Generic Pod-agent commands

The optional Pod agent is a separate operational receiver with Docker-socket access. It is disabled by default. A Pod owner enables it only with:

- `POD_AGENT_ISSUER_URL`, the exact generic issuer URL;
- `POD_AGENT_AUDIENCE`, the exact public Pod origin.

Every command is ES256-signed, exact-audience bound, short-lived, named by a `command` claim, and carries a `jti`. The agent must not infer trust from an environment Control Plane URL or accept a caller-supplied JWKS URL.

## Security properties

- No issuer is trusted by default.
- An external issuer never defines a Pod's access policy.
- Every browser-to-Pod session exchange is direct; raw Pod session material never transits the issuer.
- Federation assertions have canonical HTTPS issuer and audience identifiers, bounded lifetimes, and durable replay protection in the Pod database.
- Dynamic issuer JWKS resolution is protected against local-network and DNS-rebinding requests.
- The Pod-agent trust boundary is opt-in and independent of federation identity trust.

## Rollout and compatibility

New clients use `/api/federation/*`. Retired legacy user handshake and legacy identity provisioning endpoints return an explicit retirement response. Do not add fallback calls to them.

Some legacy operational integrations still use optional external-service configuration for marketplace, lifecycle, or intelligence delivery. They are not part of the identity or membership boundary and must be migrated independently instead of being repurposed as federation trust.
