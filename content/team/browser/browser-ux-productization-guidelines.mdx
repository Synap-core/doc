# Browser UX productization guidelines

**Status:** Productization guide  
**Primary surface:** Electron Browser  
**Related concept doc:** [Browser daily cockpit UX proposal](/team/browser/daily-cockpit-ux-proposal)  
**Related design handoff:** [Browser daily cockpit design prompt](/team/design/browser-daily-cockpit-ux-design-prompt)

## One sentence

Synap Browser should become a pod cockpit: one calm desktop surface where users capture anything, review what AI wants to change, browse the pod through profiles and views, work in sessions where artifacts become durable, and unlock power by goal.

## Why this doc exists

The V2 cockpit design exploration revealed a better product grammar. It should not be copied pixel-for-pixel, but it should become the rulebook for how Browser is simplified and productized.

This doc answers:

- which UX ideas are now canonical
- which existing components and pages should be reused
- which surfaces need redesign or consolidation
- what AI designers should do and avoid
- how implementation should phase the transformation

## Product shift

The old mental model:

```text
Synap is a set of apps: Data, Views, Proposals, Reactions, Workflows, Agents,
Import, Vault, Sessions, Library, Browser, Settings.
```

The new mental model:

```text
Synap is a pod cockpit with a few universal jobs:

Capture anything.
Review what needs a decision.
Browse what the pod knows.
Work with agents until durable artifacts exist.
Build power by goal.
Inspect history and provenance when needed.
```

The implementation can still reuse the existing apps. The product should not expose them as equal nouns.

## Canonical top-level surfaces

| Surface | User meaning | Implementation base | Product action |
|---|---|---|---|
| Home | State of my pod or current workspace | `pod-home`, `dashboard`, bento view, capture/feed/proposals/session widgets | Redesign as a readable cockpit, not a generic widget grid |
| Capture | Single source of truth for input | `@synap-core/intake-ui`, capture pipeline, `CaptureEntryPoint`, `QuickCaptureWidget`, save popover, import | Make universal and variant-based |
| Library | Browse the pod by what things are | Data app, Profiles app, Views app, entity cards, entity panels, graph/search | Make Library the product label over data/views/profiles |
| Work | Active sessions and rooms | `SessionsApp`, `@synap-core/focus-sessions`, channels, artifacts, proposals, events | Redesign session detail around outputs becoming durable |
| Build | Power grouped by goal | Data Structure, Views, Bento, Cell Studio, Workflows, Agents, Playbooks, Connectors, Vault, Import | Create one build landing page that routes into existing detail views |
| Activity | What happened, provenance, audit | Reactions app, event chain, proposal timeline cells, feed cells | Keep as timeline/history, not the review inbox |
| Settings | Quiet account/system configuration | `SettingsApp`, connector settings, vault/settings, proactive settings | Simplify and remove product creation from Settings |

## Navigation rule

Default rail:

```text
Home
Capture
Library
Work
Activity
```

Secondary:

```text
Build
Settings
```

Contextual entry points:

- Home can show Needs attention, Continue, Suggested by Synap, Organized today.
- Library can open Data, Views, Profiles, Graph, Saved Views.
- Build can route into Data model, Interfaces, Automation, AI, Connections.
- Activity can route into the event chain, proposal history, run history, and provenance.

Avoid putting every existing app in the same visible hierarchy.

## Quick Capture

Quick Capture is the most important primitive to productize first.

### Product role

Quick Capture is the single input surface for the pod. It should let a user throw something at Synap before they know where it belongs.

It must support:

- text
- URL
- local file
- photo or image
- microphone / voice
- browser context
- object link to an existing entity
- source connection
- route chips for workspace, profile, session, or view

### Required variants

| Variant | Where it appears | Behavior |
|---|---|---|
| Full modal | Global shortcut, plus button, capture route | Rich input, attachments, route chips, trust copy, confirm flow |
| Home widget | Home top section | Fast capture with action chips and "stays in pod" assurance |
| Compact command bar | Shell top bar or command palette | One-line capture, URL, command, or search |
| Inline empty state | Library, Work, Build, data views | Capture into the current context |
| Browser save popover | Browser context capture | Pre-seeded URL/context with routing and confirmation |

### Experience rule

The user should not have to choose a schema before capture.

The flow is:

```text
Input -> Synap structures -> optional one-question follow-up -> review -> write.
```

Trust copy should stay visible:

```text
Not written until you confirm.
Stays in your pod.
```

### Reuse map

- Use `@synap-core/intake-ui` and its `IntakeWidget` / intake flow as the shared behavior layer.
- Reuse the capture pipeline and `useStructureCapture` rather than creating a new parser path.
- Reuse Browser `CaptureEntryPoint` semantics where available.
- Keep `CaptureFeedWidget` as the "what happened after capture" pattern on Home.
- Let Import become a deeper capture route, not a separate first-class mental model.

## Home and Bento

### Product role

Home is not a dashboard builder. Home is a readable paper-like surface that shows what the pod is doing and what the user should do next.

It should answer:

- What needs my attention?
- What can I continue?
- What did Synap organize today?
- What did Synap notice?
- What sources and agents are active?

### Bento redesign rule

The bento grid should feel like a paper surface with placed blocks, not a developer grid of unrelated widgets.

Every block should have a clear reading pattern:

```text
Title
Short explanation or state
Useful content
Route to detail
```

Blocks can be:

- rows
- lists
- summaries
- review blocks
- continuation cards
- proactive insights
- embedded views
- compact source/status blocks

Do not make every block a generic card with icon, title, paragraph, and button.

### Recommended Home sections

1. Universal capture input.
2. Needs attention summary.
3. Continue sessions.
4. Synap noticed.
5. Organized today.
6. Sources and sync.
7. Spaces or active contexts.

### Reuse map

- Use `DashboardView` and the bento system as the layout base.
- Reuse widgets from `@synap/views-bento`, especially quick capture, entity lists, sections, active sessions, feed, status, and view blocks.
- Reuse Browser `CaptureFeedWidget` for organized-today/history patterns.
- Reuse proposal cells for Needs attention summaries, but do not expose raw proposal terminology in Home.
- Reuse focus-session cards for Continue.

### Needs update

- Bento blocks need better density modes: row, list, card, full panel.
- Blocks need route affordances into detail pages, not only static display.
- Home should have a stronger visual hierarchy than a uniform card grid.
- Widget configuration should be secondary; reading and action should be primary.

## Library

### Product role

Library is the user's knowledge browser. It is organized by what things are, not where files are stored.

Library should unify:

- profiles
- saved views
- recent entities
- search
- entity cards
- graph / relations
- documents and sources

### Product decision

Use "Library" as the user-facing label, even if implementation reuses Data, Profiles, and Views.

This reverses the current product language where Data is primary and Library is deprecated. Users understand Library. Builders understand Data.

### Layout pattern

Recommended structure:

```text
Header: Library + search + Ask Synap
Left sidebar: Profiles + Saved Views
Main: card/list/grid view of entities
Right panel: selected entity detail, relations, actions
```

### Card pattern

Entity cards should become simpler and more readable:

- profile/type label
- title
- one line of semantic metadata
- relation/source count
- workspace or saved view context
- time/status when meaningful

Avoid over-rendering every property on cards.

### Reuse map

- Use `DataApp` as the likely implementation base.
- Reuse `EntityTypeSidebar`, `DataListView`, `DataGridView`, `DataGraphView`, and save-as-view behavior.
- Reuse `@synap-core/entity-card` for entity display and detail renderers.
- Reuse `@synap-core/entity-views` for side panels and entity full/detail views.
- Reuse Views Management for saved views and creation flows.
- Reuse graph view when the user needs "knowledge has shape."

### Needs update

- Data, Profiles, Views, and old Library should feel like one Library surface.
- Saved Views need to sit beside Profiles in the main browsing sidebar.
- Entity cards need a calmer default display.
- Ask Synap should be contextual to current selection, filter, or profile.

## Work and Sessions

### Product role

Work is where goals become durable artifacts.

The core experience:

```text
User starts or resumes a session.
Agents and humans work in a room.
Artifacts appear live.
Changes become reviewable proposals.
Approved outputs become durable entities, documents, views, or cells.
```

### Session detail layout

Recommended structure:

```text
Top banner: goal, status, participants, expected outputs, run controls
Main: room channel for steering and evidence of progress
Right: proposals, event timeline, sources
Bottom or secondary: artifacts becoming durable
```

### Product warning

Do not let Work become chat-first. The room stream is important, but the product value is durable output.

The design should emphasize:

- outputs
- artifacts
- proposals
- sources
- timeline
- participants and permissions

### Reuse map

- Use `SessionsApp` as the base.
- Reuse `@synap-core/focus-sessions`: `SessionBanner`, `SessionRoom`, `SessionCard`, `SessionPartyCluster`, and `buildSessionRoomData`.
- Reuse channels for room messages and steering.
- Reuse proposal review components for session-scoped proposals.
- Reuse event chain data for session timeline.
- Reuse artifacts/document/view/cell rendering through the cell runtime.

### Needs update

- Session overview cards can follow the V2 cockpit card pattern.
- Session detail should make artifacts and expected outputs more prominent.
- Save as playbook should be part of the session lifecycle, not a detached feature.
- Session output should route directly into Library and Home "Continue."

## Build

### Product role

Build is the power surface. It should be organized by what the user wants to do, not by Synap's internal primitives.

Canonical groups:

| Group | User meaning | Existing bases |
|---|---|---|
| Data model | Shape what the pod knows | Data Structure, Profiles, properties, relations, graph |
| Interfaces | Shape how data is seen | Views, bento dashboards, cells, artifacts |
| Automation | Make things happen | Workflows, reactions, webhooks, run history |
| AI | Shape agents and intelligence | Agents, playbooks, skills, governance, proactive settings |
| Connections | Bring data in and keep it yours | Import, connectors, vault, sync |

### Build landing page

Create a Build landing page with:

- Suggested by Synap
- Power, by goal
- Recent builds or changes
- Governance reminder

The group cards should route into existing detail views. Build should not duplicate all underlying apps.

### Suggested by Synap

Suggested build actions are powerful because they connect behavior to improvement:

- "Add a priority property because you sort tasks by hand."
- "Create a view from repeated weekly tasks."
- "Turn low-risk approvals into an automation."
- "Save this session as a playbook."
- "Reconnect Google Drive."

Each suggestion should have:

- why Synap suggested it
- preview
- build/apply action
- proposal or permission path when needed

### Reuse map

- Data model: `DataStructureApp`, `@synap/features/data-structure`, profile/property pages.
- Interfaces: `ViewsApp`, `@synap/apps/views-management`, bento view, cell runtime, Cell Studio.
- Automation: `WorkflowsApp`, flow view, reactions/event chain.
- AI: `AgentsApp`, Playbooks app, proactive settings, governance.
- Connections: Import app, connectors package, Vault app, sync/status settings.

### Needs update

- Build should be secondary in the rail, but excellent when opened.
- The first screen should be grouped by goal, not a raw app grid.
- Detail pages can remain specialized, but entry should be user-language first.
- Governance should be visible: nothing writes silently.

## Attention and Activity

### Product decision

Keep the concepts separate:

```text
Attention = what needs my decision.
Activity = what happened.
```

For now, keep Activity/Event Chain as the existing app and do not replace it with a new Attention app until the review surface is ready.

### Attention patterns to reuse

Attention can appear in Home and Work before becoming a full app:

- Home Needs attention section.
- Session proposal panel.
- Import mapping review.
- Vault permission request.
- Build suggestion review.

### Activity role

Activity should remain the forensic/provenance surface:

- event chain
- automation runs
- AI actions
- proposal history
- imported events
- system sync

This is where a user goes to answer "what happened?" not "what should I approve now?"

### Reuse map

- Use Reactions app for Activity.
- Use Proposals feature components for review cards and detail panels.
- Use proposal timeline cells for audit/provenance.
- Use event chain views for durable history.

## Settings

Settings should become quieter and simpler.

Settings is for:

- account
- pod connection
- sync
- security
- notifications
- defaults
- advanced/system configuration

Settings should not be the main place for:

- building views
- shaping data model
- creating automations
- reviewing AI changes
- connecting everyday sources

Those belong in Build, Capture, Attention, or Library.

## Detail pages

Synap needs stronger detail routes. Lists and bento blocks should always lead somewhere useful.

Canonical detail patterns:

| Detail type | Base |
|---|---|
| Entity detail | entity-views / entity-card full view |
| Profile detail | Profiles/Data model |
| View detail | Views Management + view renderer |
| Session detail | SessionsApp + focus-sessions |
| Artifact detail | cell runtime / document / view renderer |
| Connector detail | connectors package |
| Workflow detail | Workflows app |
| Proposal detail | proposals feature |
| Event detail | Activity/Reactions/event chain |

Do not create isolated detail UIs if a cell, view, entity detail, or existing app can render the object.

## Component principles

### 1. Reuse before redesign

The productization layer should compose existing primitives:

- cells
- views
- entity cards
- intake
- proposals
- channels
- focus sessions
- workflows
- connectors
- vault

Only create new components when a pattern is missing across multiple surfaces.

### 2. Surface-aware components

The same component should adapt by placement:

```text
bento block
side panel
full page
modal
inline empty state
```

Quick Capture, entity cards, proposal cards, session cards, and view cards all need placement-aware density.

### 3. User-language shell, platform-language detail

Top-level labels should be simple:

- Capture
- Library
- Work
- Build
- Activity
- Settings

Inside detail pages, platform nouns can appear:

- entity
- profile
- view
- cell
- proposal
- relation
- workflow
- connector

### 4. Route every block

Every meaningful block should answer:

- What is this?
- Why is it here?
- What can I do?
- Where do I go deeper?

No decorative widgets.

## Design guidelines for AI designers

### Do

- Design desktop-first, dense, calm software.
- Use warm, restrained surfaces, but respect Synap's dark-first product direction.
- Make Quick Capture the hero interaction, not a marketing hero.
- Make Home read like a living paper, not a widget store.
- Put Profiles and Saved Views together in Library.
- Make Work output-first and source-aware.
- Group Build by goals: Data model, Interfaces, Automation, AI, Connections.
- Show governance calmly: "Not written until you confirm", "Stays in your pod", "Nothing writes silently."
- Use status, time, relation count, source count, and risk only when they help scanning.

### Do not

- Do not copy a beige/light theme as the final brand direction without dark-first validation.
- Do not make every surface a grid of identical cards.
- Do not expose raw internal apps as the main IA.
- Do not turn Bento into a developer layout editor on first open.
- Do not make Library feel like a database admin table.
- Do not make Work a chat app with panels.
- Do not make Build a settings page.
- Do not hide governance behind technical proposal language.
- Do not create a separate renderer when a cell/view/entity renderer exists.
- Do not make AI feel like it is writing silently.

## Implementation phases

### Phase 1: Make the current product understandable

- Rename/reframe top-level Browser IA around Home, Capture, Library, Work, Activity, Build.
- Make Library a shell over Data + Views + Profiles.
- Add or refine Quick Capture variants.
- Update Home bento defaults toward cockpit sections.
- Keep Activity/Reactions as the history surface.

### Phase 2: Redesign the reusable cards and blocks

- Entity cards: simpler card/list default.
- Bento blocks: row/list/card/full density modes.
- Session cards: continuation-oriented.
- Proposal/review cards: clearer why/what/affects.
- Build cards: grouped by user goal.

### Phase 3: Productize Work and Build

- Update session detail around outputs becoming durable.
- Add Build landing page.
- Route Build groups into existing app/detail bases.
- Add Suggested by Synap build cards.

### Phase 4: Deepen intelligence and continuity

- Add contextual Ask Synap to Library and Build.
- Add proactive Home insights tied to evidence.
- Add cross-surface continuity: capture -> review -> library -> work -> build suggestion.
- Add better event/provenance links from every object.

## Acceptance criteria

A redesigned Browser path is product-ready when:

- a new user can capture something useful in under 3 seconds
- the user can tell what changed and what needs review in under 10 seconds
- Library shows profiles and saved views in one coherent browsing model
- Work shows durable outputs, not just conversation
- Build explains power by goal, not by primitive list
- Activity answers "what happened?"
- every AI mutation remains reviewable, reversible, and tied to pod governance
- the implementation reuses cells, views, entity cards, intake, proposals, sessions, and existing app detail routes

## Product alignment

**Alignment: HIGH**

This direction fits Synap's V0 and north star because it does not invent a new product silo. It reorganizes the existing substrate into a usable daily surface:

- **Capture-first:** Quick Capture becomes the universal input primitive.
- **Emergent complexity:** Bento, Library, Work, and Build compose cells, views, entities, channels, and proposals.
- **Human-in-the-loop:** Attention patterns make AI writes more visible and controlled.
- **Progressive disclosure:** Build groups power by intent and keeps low-level primitives behind detail routes.
- **Sovereign:** The pod remains the source of truth, with trust copy and review flows visible.
- **BYO-agent ready:** Work sessions can show agent-produced artifacts materializing live in Browser.
