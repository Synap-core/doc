# Synap Authentication Architecture

## The boundary

Synap has two independent authentication domains:

| Domain | Owns | Does not own |
|---|---|---|
| Account service / Control Plane | Accounts, passwords, recovery, sessions, invitations, and a ledger of the Pods related to its users | Pod sessions, Pod-local users, or Pod membership policy |
| Data Pod | Local users, Kratos identities and sessions, memberships, workspaces, projects, and trusted-issuer approval | Control Plane user IDs, Control Plane Pod records, or account-service password state |

An authenticated account-service user is not implicitly authenticated with any Pod. A browser or app bridges the two domains with short-lived assertions; it never relays a raw Pod session token to the account service.

`@synap-core/auth` is the shared client boundary. It restores Control Plane and Pod sessions independently, keeps Pod connections scoped to the Pod origin, and sends federation assertions directly to the selected Pod.

## Signed-in account, no Pod selected

On app reload, a valid account-service session is sufficient to restore the account state. The app must not return to the email/password screen merely because no Pod session has been restored.

1. Restore the account session.
2. Read the account service's Pod relationship ledger.
3. If there is one eligible Pod, offer or attempt a direct federation exchange.
4. If there are several, show the Pod picker.
5. If there are none, offer to add an existing Pod URL or provision one through the appropriate product flow.

The ledger is a discovery projection. The Pod remains the authority for local access.

## Federation sign-in

```text
User signs in to account service
        |
        v
Account service selects a ledger relationship and signs a user-exchange assertion
        |
        v
Browser -> Pod: POST /api/federation/exchange { assertion }
        |
        v
Pod verifies approved issuer + exact audience + expiry + purpose + durable jti
        |
        v
Pod resolves (issuer, opaque subject), checks local membership, and mints its own session
```

The assertion is not a bearer Pod session and cannot establish access for an unlinked subject. The Pod must already have an approved issuer and an identity link for that `(issuer, subject)` pair.

## Direct Pod sign-in

Every Pod also supports its own direct authentication. A user may sign in with the Pod's normal login/recovery flow without being signed in to any account service. This is the self-hosted and outage-safe path.

When an app has an account session but the selected Pod rejects the federation exchange, preserve the account session and return the user to Pod selection or direct Pod login. Do not convert an ordinary workspace/API error into an account logout.

## Add a Pod to an account

Adding an existing Pod proves local access without giving the local session to the account service:

```text
Account session -> account service: create identity-link intent
Account service -> browser: identity-link assertion
Browser (direct Pod session) -> Pod: POST /api/federation/identity-links
Pod -> browser: one-time receipt
Browser -> account service: intent + receipt
Account service -> Pod: consume receipt server-to-server
Account service -> ledger: record Pod-authoritative relationship
```

The receipt is single-use. A client must never send a Pod session cookie, session token, or password to the account service as part of this flow.

## Invitations and scoped access

The Control Plane can own an invitation's delivery and acceptance state. Once the recipient has an account, it may issue an `access-grant` assertion naming exactly one Pod-local workspace or project. The Pod verifies the issuer's `membership:grant` capability and the local target before it creates or updates its own membership.

Direct invitations created in the Pod continue to work without the Control Plane. They use Pod-local authentication and remain the fallback for self-hosted installations.

## Password reset and recovery

Password recovery belongs to the system that owns the credential:

- Account-service recovery emails return to the callback URL supplied by the requesting app after the account password has changed.
- Pod-local recovery uses the Pod's own Kratos recovery flow and callback origin.

Apps use the shared auth UI and callback contract; they do not reimplement password-reset mail logic or copy credentials between the two systems.

## Fresh managed Pod bootstrap

A fresh managed Pod has no local owner or trusted issuer. Its installer provides a Pod-local bootstrap secret. An orchestrator can send a short-lived generic `initial-owner-bootstrap` assertion directly to `POST /api/federation/bootstrap`. The Pod creates its first local owner and records a generic issuer-subject identity link. The assertion contains no Control Plane-specific identifiers or persisted external configuration.

Self-hosted Pods can create their first owner locally instead.

## Retired bridge

The former handshake bridge is retired:

- `POST /api/handshake`
- `POST /pods/handshake` and `/pods/handshake-jwt`
- `POST /api/provision/connect`
- `POST /api/provision/seed-trust`
- `POST /api/provision/seed-admin`

These endpoints must not be used as a compatibility fallback. New clients use the generic `/api/federation/*` routes: `bootstrap`, `identity-links`, `identity-links/consume`, `access-grants`, and `exchange`.

## Security invariants

- The Pod trusts no issuer by default; a local owner approves it.
- Assertions are ES256-signed, issuer- and exact-audience-bound, purpose-limited, short-lived, and replay-protected durably in the Pod database.
- Dynamic JWKS resolution rejects local/private network and DNS-rebinding targets.
- The Pod agent is a separate, opt-in operational trust boundary; it does not grant human identity or Pod membership.
- Optional Control Plane settings for marketplace, lifecycle, billing, or intelligence delivery are not authentication or membership state.
